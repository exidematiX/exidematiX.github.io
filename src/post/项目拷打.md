# 地下城探险

## 项目背景与个人职责

- 项目类型：多人局域网联机游戏。
- 核心技术问题：在不直接同步完整状态的情况下，让多个客户端按照相同输入得到一致逻辑结果。
- 我的职责：网络框架、传输层消息处理、帧同步流程、客户端预测与重连方案，以及部分AI和碰撞逻辑。
- 面试时需要补充：项目人数、运行平台、实际网络环境、自己独立完成的代码范围和最终测试数据。

## 网络框架总体设计

### 网络分层

项目网络可以按以下层次说明：

```text
游戏逻辑层
    ↓
帧同步层：输入采集、帧组装、帧执行、回滚与校验
    ↓
消息层：消息类型、序列号、连接状态、协议版本
    ↓
可靠传输层：KCP或自研可靠UDP机制
    ↓
UDP
```

原始记录中同时出现了“KCP”和“自研可靠UDP”。面试前必须根据真实代码确定以下情况：

- 如果使用KCP，KCP负责底层可靠传输，自研部分应重点解释帧输入冗余、帧确认、状态校验和业务消息管理。
- 如果没有真正使用KCP，则应删除KCP表述，完整介绍自研序列号、ACK位图、重传和拥塞处理。
- 如果两者同时使用，必须明确KCP和业务层各自解决的问题，避免在两层重复可靠传输。

### 网络数据包

![帧同步数据包设计](项目拷打.assets/image-20260416013246027.png)

通用消息包可以包含以下字段：

- 协议版本和消息类型：用于版本兼容和消息分发。
- 连接ID或玩家ID：标识连接和消息来源。
- 序列号：标识网络包顺序，需考虑无符号整数回绕。
- ACK：表示最新确认的序列号。
- ACK位图：表示最近若干个历史包是否已经收到。
- 帧号：标识输入或状态属于哪一个逻辑帧。
- Payload长度和数据：方便解析和校验。
- 校验字段：用于发现数据损坏或协议解析错误。

帧输入数据可以设计为：

```csharp
public readonly struct FrameInput
{
    public readonly int PlayerId;
    public readonly int FrameId;
    public readonly byte InputMask;
    public readonly FixedVector2 AimDirection;

    public FrameInput(int playerId, int frameId, byte inputMask,
        FixedVector2 aimDirection)
    {
        PlayerId = playerId;
        FrameId = frameId;
        InputMask = inputMask;
        AimDirection = aimDirection;
    }
}
```

实际协议还需要说明序列化方式、字节序、包大小上限、非法帧号处理和协议版本兼容。

## 帧同步方案

### 基本设计

- 逻辑帧和渲染帧分离。
- 逻辑帧固定为20 FPS，每个逻辑帧的时间步为50毫秒。
- 每个逻辑帧采集一次本地输入，输入而不是Transform作为主要同步内容。
- 客户端根据帧号缓存输入，所有客户端按照相同的帧号和固定顺序执行逻辑。
- 渲染帧读取逻辑状态，并通过插值或纠正平滑表现。
- 所有关键逻辑必须使用固定时间步，不能依赖渲染帧的`Time.deltaTime`。

### 输入发送与服务器广播

- 客户端在每个逻辑帧采集本地输入。
- 为应对偶发丢包，一个输入包可以携带当前帧和最近若干帧输入；这属于应用层冗余，不等同于KCP的可靠传输。
- 服务器收集各客户端输入，在截止时间前等待输入到齐。
- 超过截止时间仍未收到的输入，可以使用上一帧输入、预设空输入或服务器策略补位。
- 服务器将同一逻辑帧的完整输入集合广播给所有客户端，客户端必须按照帧号顺序执行。
- 截止时间、输入补位策略和最大等待时间需要通过延迟、抖动和可接受操作延迟测试得到，不能只给出没有依据的固定数值。

### 确定性模拟

帧同步要求相同的初始状态、相同的输入和相同的执行顺序得到相同的逻辑结果。可能破坏确定性的因素包括：

- 不同平台或编译器的浮点运算差异。
- Unity物理引擎的浮点计算、线程调度和执行顺序差异。
- 动态生成或版本不一致的NavMesh。
- 使用系统时间或渲染帧时间参与逻辑计算。
- 随机数种子、随机数调用顺序或不同实体调用次数不一致。
- 容器遍历顺序、网络到达顺序和未定义的对象更新顺序。

对应处理方式包括：

- 关键逻辑使用定点数或确定性数学库，并处理溢出、舍入和范围问题。
- 逻辑使用固定时间步，渲染只负责表现。
- 不直接依赖Unity物理模拟，必要时使用自研的定点数碰撞和运动逻辑。
- 使用预烘焙、版本一致的寻路数据；A*需要固定节点编号、邻居遍历顺序和Tie Break规则。
- 使用对局种子初始化确定性随机数。更稳妥的种子可以由对局种子、帧号、实体ID和行为ID共同生成，不能只使用帧号。
- 定期计算关键状态哈希，由服务器或各客户端比较，用于尽早发现状态分叉。

### 预测输入与回滚

这里需要区分两类预测：

- **缺席输入预测**：某个玩家的输入未及时到达时，暂时沿用上一帧输入或使用空输入，保证逻辑继续推进。
- **客户端预测**：本地客户端先执行本地玩家输入，减少操作延迟，收到服务器权威结果后再校正。

如果预测结果错误，客户端需要：

1. 保存最近若干帧的输入历史。
2. 保存关键逻辑状态快照。
3. 恢复到服务器确认的正确帧。
4. 从该帧重新执行输入直到当前帧。
5. 将逻辑状态和渲染状态分离，使用插值或纠正速度降低视觉上的瞬移。

攻击、伤害和奖励不能简单地全部“不预测”或全部预测。通常需要区分本地操作反馈、动画和特效、碰撞判定、伤害结算以及不可回滚的外部副作用。

### 状态校验与不同步处理

- 客户端定期对关键逻辑状态计算哈希，例如实体位置、生命值、状态和随机数状态。
- 服务器发现客户端哈希不一致时，可以发送关键帧快照或要求客户端重新追帧。
- 快照只保存可重建逻辑所需的数据，不保存特效、音效和临时渲染对象。
- 重放必须避免重复触发奖励、网络请求、音效和其他不可回滚副作用。
- 日志中应记录帧号、输入、随机种子和状态哈希，方便定位首次分叉帧，而不是等到最终画面完全不同后再排查。

## 可靠UDP与消息处理

### ACK位图

- `ack`表示最新确认的序列号。
- `ackBitfield`的每一位表示更早若干个序列号是否收到。
- 位图可以一次确认多个历史包，减少ACK数量和确认延迟。
- 序列号比较必须处理回绕，不能直接使用普通整数的大小比较。
- 位图只解决确认表达效率，不自动解决拥塞、重传和连接生命周期。

### 重传与RTO

- 每个需要可靠传输的包保存发送时间、重传次数和当前状态。
- RTO应根据平滑RTT和RTT波动动态估算，固定100毫秒只能作为特定测试环境的参数，不能作为通用结论。
- 快速重传可以根据重复ACK、ACK缺口或连续确认信息触发。
- 重传采用退避策略，超过最大重传次数后进入断线或状态恢复流程。
- 未确认包不建议每帧完整遍历，可以使用按超时时间排序的队列、最小堆或时间轮降低扫描成本。

### 乱序与丢包

- 收到包后先进行序列号校验、重复包判断和协议校验。
- 乱序包暂存在接收缓冲区，只有满足连续序列后才向上层交付。
- 帧输入可以使用帧号作为索引，放入环形缓冲区；缓冲区满时必须明确丢弃旧帧还是触发错误。
- 对帧同步而言，是否能跳过丢失帧取决于业务；不能把所有可靠消息和实时输入使用同一种策略。
- UDP没有自动拥塞控制。自研可靠UDP仍然需要限制发送窗口、重传速度和带宽，避免丢包时继续放大拥塞。

## 网络框架与Unity网络框架的区别

- Unity的Netcode for GameObjects是网络框架，不应简单概括为“只有状态同步”；它提供Server Authority、NetworkVariable、RPC等能力，具体同步模型取决于项目设计。
- Mirror等框架也可以实现RPC、命令和状态同步，框架名称不等于固定的同步策略。
- 本项目的核心区别是：自研部分围绕确定性帧同步设计，主要同步输入并要求客户端按相同帧顺序运行；Unity Netcode默认更适合服务器权威的对象状态、RPC和网络变量同步。
- 比较时应从同步对象、权威端、可靠性、预测回滚、带宽、确定性要求和开发成本几个维度说明，而不是只说“一个是状态同步、一个是帧同步”。

## 线程安全与主线程调度

- `ConcurrentQueue<T>`适合多个线程安全地生产和消费消息，具体实现使用原子操作和必要的同步机制，不能把所有并发容器简单概括为完全无锁。
- 网络线程不应直接操作Unity对象，应将收到的消息放入线程安全队列，再由主线程或逻辑线程在固定时机消费。
- 共享状态需要明确所有权、读写线程和生命周期，不能只替换成`ConcurrentQueue`就认为整个系统线程安全。
- 网络线程与Unity主线程之间可以使用生产者消费者模型，并限制每帧处理的消息数量，避免网络突发阻塞渲染。

## 断线重连

### 通用重连流程

1. 通过心跳、超时和连接状态机检测连接异常。
2. 使用退避时间和最大尝试次数发起重连。
3. 重新认证并恢复会话ID、玩家ID和协议版本。
4. 同步服务器当前状态或获取最近快照。
5. 处理重连期间的未完成请求，使用请求ID和幂等逻辑避免重复执行。
6. 恢复UI、输入、逻辑和渲染状态。

### WebSocket

- WebSocket通过HTTP升级握手建立长连接，属于应用层协议，底层通常使用TCP。
- 它支持全双工通信，服务器可以主动向客户端推送消息。
- 需要处理Ping/Pong、关闭帧、异常断开、消息积压和重连。
- WebSocket仍然受TCP字节流和队头阻塞影响，不能把它当成实时可靠UDP。

### 帧同步重连

- 重连期间服务器继续保存该玩家的输入或使用缺席输入策略。
- 客户端重新握手后获取最近的逻辑快照和之后的输入序列。
- 客户端从快照帧开始重放到当前帧，追帧完成后再恢复正常渲染。
- 快照周期应根据状态大小、重演耗时、带宽和内存进行选择。
- 通常采用“定期快照 + 输入日志”，而不是从第0帧完整重演。
- 追帧期间可以提高逻辑模拟速度，但要限制CPU占用，不能阻塞其他玩家的正常表现。

## 敌人AI寻路

### 可行走判断

- 射线检测适合判断局部地面、视线和障碍，不适合单独承担完整路径搜索。
- 可行走区域应使用导航网格、网格地图或预处理的图结构表示。
- 动态障碍需要通过局部避障、导航数据更新或重新规划处理。

### A*算法

- A*是在Dijkstra基础上加入启发函数的最短路径搜索算法。
- Open List保存待考察节点，使用小根堆可以快速取出最小`F`值节点。
- Closed Set记录已经处理的节点，适合使用集合结构。
- 还需要维护每个节点的`GScore`、父节点和必要的版本信息。
- `F = G + H`，`G`是起点到当前节点的实际代价，`H`是当前节点到终点的估计代价。
- 曼哈顿距离适合四方向网格；允许斜向移动时通常使用对角距离或Octile距离；欧几里得距离是否可采纳取决于移动规则和边权。
- 使用小根堆后，常见复杂度约为`O((V + E) log V)`，具体取决于图结构和实现。
- `F`相同时可以比较`H`，还应固定节点编号或插入顺序，以保证结果确定。

### A*优化

- 路径缓存：相同地图版本、起点区域和目标区域可以复用路径。
- 分帧寻路：限制每帧搜索节点数，避免一次请求阻塞主线程。
- 请求合并：对同一目标区域的多个请求复用搜索结果。
- 分层寻路：先在区域图上搜索，再在局部网格上精确搜索。
- 双向A*：适合起点和终点明确、图结构合适的场景。
- Jump Point Search：适合规则网格并减少对称路径搜索。
- 路径平滑：在得到网格路径后进行拐点合并或漏斗算法处理。
- 多NPC场景还要结合路径共享、局部避障、寻路队列和远处AI降频。

## 行为树与状态机

### 行为树节点

- 节点通常返回`Success`、`Failure`或`Running`。
- Sequence按顺序执行子节点，遇到Failure或Running就停止，全部Success才返回Success。
- Selector按顺序执行子节点，遇到Success或Running就停止，全部Failure才返回Failure。
- Parallel需要明确成功阈值、失败阈值和Running节点的处理策略。
- Decorator包装单个子节点，可以实现条件、反转结果、重复、超时和冷却等功能。
- Blackboard保存感知、目标、路径、资源和状态等共享数据。

### Tick与性能

- 不建议每帧完整遍历所有NPC的整棵行为树。
- 可以只Tick当前活动路径，使用事件驱动，按距离分级，分帧执行或降低远处NPC更新频率。
- Blackboard应尽量使用类型安全的数据访问，避免大量字符串键和`object`导致运行时错误及装箱。

### 行为树与状态机

- 行为树适合表达层级化、可复用的决策流程。
- 状态机适合状态数量有限、转换关系明确的角色逻辑。
- 复杂角色可以使用层次状态机和行为树组合，而不是简单地二选一。

### 多NPC复用

- 多个NPC可以共享行为树结构和节点配置。
- 每个NPC必须拥有独立的Blackboard和运行时状态，节点不能保存跨NPC的可变状态。
- 可将感知、寻路、战斗和动画拆成独立服务或组件，行为树只负责决策和编排。

## 状态机问题

### 解决状态抖动和循环切换

- 使用进入和退出阈值不同的滞回条件。
- 为状态设置最短驻留时间或切换冷却时间。
- 使用转换优先级，避免多个条件同时满足时结果不稳定。
- 将状态机拆成层次结构，避免所有状态互相直接引用。
- 对目标距离、血量、视野等连续条件使用缓冲区。
- 直接改成行为树不是唯一解决方案，应根据状态数量和转换复杂度选择结构。

---

## AABB碰撞算法

- AABB是轴对齐包围盒，盒子的边界始终与坐标轴平行。
- 二维AABB需要检查x轴和y轴区间是否都相交；三维AABB还需要检查z轴。
- 两个AABB重叠的条件是每个轴上的区间都重叠，例如`minA.x <= maxB.x && maxA.x >= minB.x`，其他轴同理。
- AABB测试速度快，适合Broad Phase，但只能判断可能碰撞，不能精确处理旋转后的复杂模型。
- 需要明确边界接触是否算碰撞，以及使用严格不等式还是非严格不等式。
- 大量对象不能直接两两检测，应结合空间哈希、四叉树、八叉树或网格分区。

## Event系统

### 基本设计

- 事件系统可以通过事件类型、消息对象或泛型事件传递模块间变化。
- `Dictionary<int, List<Action<object[]>>>`实现简单，但存在类型不安全、装箱、数组分配和参数顺序错误等问题。
- 枚举作为事件ID不是天然错误；多人协作问题可以通过模块化事件定义、命名空间、类型化消息或代码生成解决。
- 推荐使用类型安全事件，例如每种事件对应独立的消息类型或泛型事件通道。

### 生命周期与注销

- 订阅时返回`IDisposable`或取消句柄，由订阅方持有并在销毁时注销。
- Unity对象禁用、销毁和场景切换时都要考虑取消订阅。
- 不能只依赖“哨兵组件”自动清理而忽略静态事件、全局事件总线和跨场景对象。
- 事件总线会隐藏模块依赖，使用时应限制事件范围、记录发布者和订阅者，并防止循环事件和通知风暴。

# 项目重构与架构选择

## 为什么从帧同步改为状态同步

帧同步要求相同输入、相同初始状态和相同执行顺序能够产生相同结果。本项目中的物理系统、寻路数据、AI随机决策和执行顺序难以完全保证确定性，因此继续扩大帧同步范围会增加调试和维护成本。

改为状态同步或服务器权威同步的理由可以表述为：

- 服务器统一负责关键逻辑和最终结果。
- 客户端主要负责输入、表现和预测，不能直接决定奖励、伤害和资源结果。
- 不同客户端的物理和渲染差异不会直接造成全局状态分叉。
- 调试时可以直接比较服务器快照和客户端状态。
- 代价是服务器计算、状态带宽、插值、预测和校正逻辑增加。

如果项目只是部分改造，应明确哪些模块仍然使用帧同步，哪些模块使用状态同步，不要笼统说“项目改成了状态同步”。

## 帧同步与状态同步对比

| 场景 | 常见方案 | 主要原因 |
| --- | --- | --- |
| 格斗、RTS | 帧同步或混合方案 | 输入量小，对一致性和帧级响应要求高 |
| FPS | 服务器权威状态同步加客户端预测 | 需要反作弊、预测和高频状态校正 |
| SLG、MMO | 状态同步 | 逻辑复杂、玩家多，不适合等待所有输入 |
| 回合制卡牌 | 状态同步通常更简单 | 操作离散，对帧级同步要求低 |
| MOBA | 服务器权威或混合方案 | 需要预测、插值、状态校正和权威结算 |

具体方案取决于玩家数量、操作实时性、逻辑确定性、反作弊要求、服务器成本和网络条件，不能只按游戏类型绝对判断。

## MVC与ECS

- MVC解决的是数据、界面和控制职责的组织问题。
- ECS解决的是大量实体的数据布局、查询和批量处理问题。
- ECS不是MVC的直接替代品，Controller职责膨胀可以通过Service、UseCase、Command、Presenter和消息处理器拆分。
- ECS适合大量同构实体，例如子弹、单位、粒子和移动对象；复杂UI通常更适合专门的UI架构。
- ECS不保证自动消除GC、虚函数或耦合，仍然需要合理的数据访问、系统依赖和生命周期管理。
- 项目重构时应说明迁移范围、收益、成本、兼容方案和最终保留的MVC部分。

# SLG实习项目

## 项目背景与个人职责

- 项目类型：SLG客户端开发。
- 负责模块：建筑系统、资源生产、英雄招募、UI逻辑和数据绑定。
- 参与内容：协议解析、客户端状态更新、服务器Push处理和异常数据校验。
- 优化内容：列表Item复用、UI刷新合并、对象池和界面生命周期管理。
- 面试前需要补充：使用的具体网络协议、UI框架、数据规模、列表数量、优化前后指标以及个人提交范围。

## SLG系统的共同原则

- 策划配置表提供静态规则和数值。
- 服务器同步数据提供玩家当前状态和权威结果。
- 客户端可以做合法性预检查和本地表现，但不能信任客户端校验结果。
- 资源、建筑完成、奖励领取和消耗必须由服务器最终校验。
- 客户端Model负责保存当前状态，View负责表现，Controller或Service负责流程编排，NetworkHandler负责协议转换。

## 建筑系统

### 核心功能

- 玩家选择建筑类型和位置。
- 客户端预检查地块是否占用、前置条件是否满足和资源是否足够。
- 客户端发送建造、升级、取消或拆除请求。
- 服务器验证配置、地块、资源、队列和玩家权限。
- 服务器返回权威结果或通过Push广播状态变化。
- 客户端更新Model并驱动UI显示倒计时、等级和资源变化。

### 客户端数据结构

建筑Model可以包含：

- `BuildingId`：建筑实例唯一ID。
- `ConfigId`：策划配置表ID。
- `Position`：建筑位置或地块信息。
- `Level`：当前等级。
- `State`：空闲、建造中、升级中、生产中、损坏等状态。
- `StartTime`：服务器时间戳。
- `EndTime`：服务器时间戳。
- `QueueId`：建造或生产队列ID。
- `Version`：服务器状态版本或序列号。

### 建筑升级流程

```text
点击升级
    ↓
客户端预检查
    ↓
发送请求ID和建筑版本
    ↓
服务器校验资源、等级、队列和前置条件
    ↓
服务器扣除资源并生成结束时间
    ↓
返回响应并发送状态Push
    ↓
客户端更新Model和UI倒计时
    ↓
完成时请求领取或等待服务器Push确认
```

- 客户端预检查只用于提前提示，不能替代服务器校验。
- 请求需要带请求ID，超时重试时服务端应保证幂等。
- 客户端收到失败响应时，应根据服务器状态回滚本地预表现。
- 状态Push可能先于请求响应到达，客户端需要使用版本号或序列号处理乱序。

## 资源生产系统

### 数据模型

- 资源类型、当前数量、容量上限和产率。
- 最后结算时间或生产开始时间。
- 当前服务器时间偏移和状态版本。
- 生产建筑、生产队列、加速效果和领取状态。

### 生产结算

- 不建议客户端和服务器每秒真实累加资源。
- 服务器通常根据开始时间、结束时间、产率、容量和当前服务器时间计算理论产量。
- 玩家打开页面、登录、领取资源或收到Push时进行结算。
- 客户端可以用服务器时间估算当前显示值，但最终资源数量以服务器结果为准。
- 需要处理重复领取、请求超时、服务器时间回退、容量溢出和配置版本变化。

## 英雄招募系统

- 招募配置由策划表提供，包含消耗、概率、保底、英雄池和活动版本。
- 客户端展示配置和动画，抽取结果由服务器生成并返回。
- 抽取请求需要请求ID和幂等处理，避免重试造成重复抽取或重复扣费。
- 结果响应与资源扣除、背包变化和保底计数应使用同一版本或事务结果。
- UI可以提前播放表现，但不能提前确定最终英雄结果。

## 时间同步

- 建筑结束时间应使用服务器时间戳或统一的Unix时间，不要让客户端直接使用本地墙上时间计算逻辑结果。
- 登录或请求时估算服务器时间偏移，并结合往返时间降低误差。
- 倒计时显示可以使用“服务器结束时间 - 当前估算服务器时间”。
- 客户端本地系统时间可能被修改，逻辑计时应优先使用服务器时间和单调时钟。
- 只有展示本地日期时，才进行时区转换。

## MVC框架

### 职责划分

- **Model**：保存业务状态和必要的数据访问接口，不直接操作UI。
- **View**：负责显示、输入和视图生命周期，不直接决定业务规则。
- **Controller或Presenter**：协调输入、服务调用、Model更新和View表现。
- **NetworkHandler**：负责协议编码、解码、请求响应匹配和Push分发。
- **Service**：封装建筑升级、资源结算和招募等业务流程，避免Controller无限膨胀。

原记录中Model同时包含静态全局数据、Update和Get方法，这容易形成全局依赖。修改时应说明哪些数据属于Model，哪些逻辑应移动到Service或Repository。

### 消息系统

- Model与View之间可以使用类型安全事件，状态变化后由View刷新。
- 跨模块通信可以使用领域事件或消息总线，但消息类型、发布者和订阅者应明确。
- 全局事件总线容易形成隐藏依赖，应限制使用范围并管理订阅生命周期。
- 同一帧内多次更新Model时，可以合并刷新请求，通过脏标记或刷新队列在统一时机更新View。
- 不一定必须在`LateUpdate`刷新，关键是保证每帧最多合并一次或按业务节流。

## 常见数据与UI问题

### 数据先到、界面未创建

- Model先更新数据，不依赖View是否存在。
- View创建时主动读取Model当前完整状态并初始化。
- View订阅事件后只接收后续变化。
- 不要把临时数据只保存在已经销毁的View中。

### View销毁后事件仍触发

- 订阅时保存取消订阅句柄。
- 在`OnDisable`、`OnDestroy`或页面生命周期结束时注销，具体选择取决于页面是否复用。
- 避免静态事件长期持有View引用。
- 防止重复打开页面造成重复订阅和一次变化多次刷新。

## UI刷新与对象复用优化

- 英雄招募列表使用固定数量的Item加缓冲区，实现列表虚拟化，而不是一次性生成所有英雄Item。
- Item复用时只更新变化的字段，避免无意义的`SetText`、换图和Layout重建。
- 资源数值频繁变化时，Model更新可以持续进行，View刷新请求通过脏标记或队列合并到统一时机。
- 减少频繁启停复杂Layout、ContentSizeFitter、Mask和大面积透明UI。
- 使用Profiler确认瓶颈是脚本、布局重建、顶点重建、批次变化还是Overdraw。

# XLua热更新

## XLua原理

- XLua通过Lua虚拟机、C#与Lua之间的桥接代码和生成代码实现互相调用。
- C#调用Lua时，通过Lua环境查找函数并传递参数。
- Lua调用C#时，通过生成的绑定代码查找类型、方法和字段，并完成参数转换。
- 委托、数组、字典、值类型和引用类型会涉及不同的转换和生命周期管理。
- 具体热补丁实现依赖XLua版本、配置和生成流程，不应简单概括为“只依赖Mono运行时重定向”。

## 热补丁流程

常见流程是：

1. C#代码标记需要热修复的类型或方法。
2. 通过配置生成桥接代码、适配代码或补丁代码。
3. 构建包中保留必要的AOT代码和元数据。
4. 启动时下载并校验Lua脚本和资源版本。
5. 初始化Lua环境，将目标调用重定向到Lua实现。
6. 热更失败时回滚到内置版本或停止加载不兼容脚本。

实际项目中还要处理脚本版本、依赖、断点续传、缓存、签名校验和灰度发布。

## IL2CPP下的限制

- IL2CPP属于AOT环境，运行时动态生成代码和反射能力受平台和裁剪影响。
- 需要提前生成必要的桥接代码、泛型元数据和类型引用，并配置代码保留。
- C#字段布局、原生结构、未生成的泛型和不支持的运行时动态行为不能简单依靠Lua解决。
- 热更新脚本不等于所有原生逻辑都能热更新，涉及原生插件、资源格式和底层结构变化时仍需发包。

# 性能优化

## Instantiate与GC

- `Instantiate`会创建Unity原生对象及其层级、组件和托管侧相关对象，产生CPU、内存和可能的托管分配开销。
- `Destroy`通常不会立即完成，频繁创建和销毁会造成生命周期管理、内存回收和峰值耗时问题。
- GC只负责托管堆对象，Unity原生对象资源和GC不是同一回事。
- GC压力可能导致主线程出现明显停顿或增量回收开销，具体取决于运行时和Unity版本。
- 优化前应使用Profiler确认是Instantiate、Destroy、脚本分配、资源加载还是UI重建导致问题。

## 对象池

对象池可以由空闲队列、活动对象集合、创建策略和容量限制组成。

- 预热：在非关键时机提前创建常用对象。
- 获取：从空闲队列取出并初始化；没有空闲对象时按策略扩容、排队或返回失败。
- 释放：停止表现、清理状态并放回空闲队列。
- 上限：防止异常请求无限创建对象。
- 销毁：场景切换或内存压力下释放多余对象。
- 不建议直接回收仍在使用的最老对象，否则可能破坏当前战斗或UI状态。
- 归还时需要重置位置、激活状态、动画、粒子、物理速度、Tween、协程、事件订阅、子物体和临时数据。
- 对象池适合高频创建销毁且结构相近的对象，不应无条件池化所有对象。

## UI优化

- 列表使用固定Item数量和复用，减少创建和销毁。
- 文本、图片和进度条只有数据变化时才刷新。
- 使用脏标记合并同一帧内的多次刷新。
- 拆分静态Canvas和频繁变化Canvas，但避免创建过多Canvas。
- 减少复杂Layout、ContentSizeFitter、Mask、无效Raycast Target和透明大面积元素。
- 使用Profiler、UI Profiler和Frame Debugger定位实际瓶颈。

## 多对象场景优化

- CPU：管理器分批Tick、时间片调度、距离分级和按需激活。
- GPU：LOD、视锥剔除、遮挡剔除、GPU Instancing和材质复用。
- 内存：对象池、资源引用计数和合理的加载卸载策略。
- 寻路：请求队列、路径缓存、分帧搜索、局部避障和远处AI降频。
- 网络：只同步必要状态，使用差量、快照压缩和不同可靠性通道。
- 优化前后都要记录CPU、GPU、GC Alloc、内存、DrawCall、网络带宽和帧时间，而不是只看一个指标。

# 常见追问

## 上一个数据包丢失但下一个数据包已经到达，如何处理

- 通过序列号判断顺序，通过接收缓冲区暂存乱序包。
- 可靠消息等待缺失包重传后按序交付。
- 可丢弃的实时表现消息可以直接使用较新的数据，避免旧消息阻塞。
- 帧同步输入可以通过输入冗余、ACK位图或快照恢复降低丢包影响。
- 需要根据消息类型选择可靠有序、可靠无序或不可靠通道。

## 红黑树与平衡二叉树

- 平衡二叉树是一个统称，目标是控制树高；AVL树和红黑树都属于平衡树。
- AVL树平衡条件更严格，查询路径通常更短，但插入删除可能进行更多旋转。
- 红黑树通过颜色规则保持近似平衡，插入删除通常旋转较少，适合频繁更新。
- 两者都能把查找、插入和删除控制在`O(log n)`。

## MVVM

- Model保存业务数据。
- View负责显示和用户输入。
- ViewModel为View提供可绑定的数据和命令，隔离View与Model。
- 数据绑定可以减少手动刷新代码，但需要处理绑定生命周期、循环更新和调试复杂度。
- MVC更强调Controller协调流程，MVVM更强调View与ViewModel之间的数据绑定；实际项目可以组合使用。

## UGUI优化

- 减少Canvas重建范围，拆分频繁变化和静态UI。
- 减少布局组件、Mask、透明大面积元素和无效射线检测。
- 使用图集和材质复用提高合批机会，但图集不保证一定减少DrawCall。
- 使用列表虚拟化和对象池减少Item创建。
- 使用Profiler和Frame Debugger判断问题来自脚本、布局、顶点、材质、批次还是Overdraw。

## Unity插件分类

- 托管插件：C#程序集，提供可直接调用的类型和方法。
- 原生插件：C/C++动态库，通过P/Invoke或Unity原生接口与C#交互。
- 编辑器插件：只在Unity编辑器运行，用于工具、导入、构建和配置。
- 资源插件：处理AssetBundle、Addressables或自定义资源格式。
- 使用插件时要考虑平台二进制、加载时机、IL2CPP、代码裁剪、线程限制和许可证。

## Unity与Lua传参

- 基础数值通常通过绑定层直接转换，但需要注意类型范围和装箱。
- 引用类型需要处理对象映射和生命周期，避免Lua长期持有已经销毁的Unity对象。
- 数组、List、Dictionary和自定义结构体需要配置对应的适配或生成代码。
- 委托传给Lua时要保存引用，避免回调对象被回收或重复注册。
- 高频调用应减少跨语言边界次数，必要时批量传递数据。

## A*还有哪些优化

- 小根堆替代线性查找。
- 路径缓存和相同目标请求合并。
- 分帧搜索和任务队列。
- 分层地图、区域图和导航网格。
- 双向A*和Jump Point Search。
- 合理的启发函数、Tie Break和路径平滑。
- 远处NPC降低寻路频率，动态障碍变化时只重算受影响路径。

## 如何设计一个游戏系统

回答“类似羊了个羊”或其他系统架构题时，可以按以下顺序：

1. 明确核心玩法、玩家数量、单局时长和是否联网。
2. 定义客户端、服务器、配置、存档和支付等边界。
3. 设计核心数据结构和状态机。
4. 说明协议、服务器权威、幂等、断线重连和异常处理。
5. 说明UI刷新、资源加载、对象池和性能风险。
6. 说明扩展性、版本兼容、热更新、监控和日志。
7. 最后说明方案的瓶颈、替代方案和取舍。

# 面试前需要补充的事实

- 地下城探险实际使用的是KCP、自研可靠UDP，还是两者组合。
- 网络框架中自己编写的模块、代码规模和与第三方库的边界。

- 定点数格式、数值范围、溢出处理和碰撞算法支持的形状。
- 状态哈希、快照、回滚和追帧是否已经真正实现，还是设计方案。
- A*运行在网格、NavMesh还是自定义图结构上，以及是否使用路径缓存。
- SLG项目使用的UI框架、协议格式、数据规模和服务器Push机制。
- UI虚拟列表、脏标记和对象池优化前后的真实性能数据。
- XLua是否运行在Mono和IL2CPP，使用了哪些生成代码和热补丁配置。
- 每个项目中个人负责的代码范围、遇到的具体Bug以及最终解决结果。
