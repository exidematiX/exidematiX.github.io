## 二、电魂网络·三消休闲游戏

### 面向对象 ECS 框架（ET 风格）

#### Q1：你们用的是哪种 ECS？先说说 ECS 的两种流派。

- ECS 即 **Entity（实体）+ Component（组件）+ System（系统）**，但业界有**两种完全不同的实现思路**：
- **数据导向 ECS（Data-Oriented）**：以 Unity DOTS 为代表，Entity 只是一个 ID，Component 是纯数据 POD，内存按 Archetype 连续存储，System 按查询批量处理，配合 Job/Burst 多线程，追求 Cache 友好和高吞吐。
- **面向对象 ECS（Object-Oriented）**：以 **ET 框架**为代表，Entity 和 Component 都是**对象**，Component 可以带数据和行为、可以继承，System 是处理某类组件的逻辑类（如 AwakeSystem/UpdateSystem）。核心目标是**解耦、复用和代码组织**，而不是极致性能。
- **我们项目用的是第二种（类似 ET）**：用实体-组件树组织游戏对象，把逻辑拆到各 System 里，主线程运行，不涉及 DOTS/Burst/Job。

#### Q2：面向对象 ECS 里 Entity、Component、System 分别是什么？

- **Entity（实体）**：一个可挂载组件的对象，本身也是容器，可以组成父子层级（树形结构），用来表达场景中的游戏对象和它们的归属关系。
- **Component（组件）**：挂到 Entity 上的数据/行为单元，在 ET 里通常也继承自 Entity，可以有自己的字段和方法，代表“这个对象拥有什么能力/数据”（如位置、血量、棋子类型、生产状态）。
- **System（系统）**：处理某类组件逻辑的类，一般通过生命周期方法（Awake/Update/Destroy 等）或事件注册的方式绑定到组件上，负责具体的业务行为。
- 三者关系可以理解为：**Entity 是骨架，Component 是肉，System 是行为**；对象通过“挂什么组件”具备什么能力。

#### Q3：它和 Unity DOTS 的数据导向 ECS 有什么本质区别？

| 维度 | 面向对象 ECS（ET 风格） | 数据导向 ECS（DOTS） |
| --- | --- | --- |
| Entity | 对象/容器，有层级 | 只是一个 ID |
| Component | 对象，可带数据+行为 | 纯数据 POD，无行为 |
| 内存布局 | 对象分散在堆上 | Archetype 连续内存 |
| 执行 | 主线程，逻辑类/生命周期方法 | 查询 + Job 多线程 + Burst |
| 主要收益 | 解耦、复用、可维护、易扩展 | 高性能、高吞吐、低 GC |
| 学习/迁移成本 | 低 | 高 |

- 关键：**面向对象 ECS 不追求 Cache 友好和极致性能**，它的价值在于把游戏逻辑按组件拆开、降低耦合、方便复用和热更；性能收益是次要的，甚至因为对象分散可能不如传统写法。

#### Q4：为什么三消项目选这种 OO ECS？

- 三消棋盘上棋子/格子数量多、类型多，用“实体 + 组件”的方式挂载能力（可消除、可下落、带特效、带倒计时），能灵活组合、便于扩展新棋子，而不用写一堆继承和 if-else。
- System 把消除、下落、补位、连锁等逻辑拆开，各自独立、便于维护和复用。
- 项目规模不需要 DOTS 那套重型方案，OO ECS 在开发效率和结构清晰度上更平衡。

#### Q5：Component 里能放逻辑吗？

- 在面向对象 ECS 里，**可以**：Component 是对象，可以带字段和方法，这也是它和纯数据 Component 的最大区别。
- 但要注意职责边界：**数据 + 与该数据强相关的局部行为**放 Component；跨组件的流程/编排逻辑放 System 或服务里，避免组件之间互相强引用形成网状依赖。
- 如果组件里塞满对其他组件的直接引用和复杂流程，就退化成普通的面向对象开发，失去解耦意义。

#### Q6：System 怎么绑定和执行？执行顺序怎么保证？

- 系统通常通过生命周期方法（Awake/Start/Update/Destroy）或注册/事件的方式绑定到组件，组件被创建/销毁/每帧更新时触发对应系统逻辑。
- 执行顺序用明确的调度顺序或层级（如固定的更新阶段）：输入 → 消除判定 → 下落 → 补位 → 连锁 → 表现触发。
- 同一帧内**逻辑先行、表现后置**，避免表现回调反过来影响逻辑；顺序敏感的连锁/结算要用固定遍历顺序，避免依赖 `Dictionary` 遍历顺序导致结果不稳定。

#### Q7：ECS 中“表现”和“逻辑”怎么同步？

- 逻辑层（组件/系统）只计算结果：哪些格子消除、哪些元素下落、产生多少分数。
- 表现层订阅逻辑事件或读逻辑结果，播放动画、特效、音效；逻辑帧和表现帧可以不同步，表现用插值追上。
- 结算类逻辑一定要等表现播完再进入下一阶段，通常用异步流程（见 UniTask 部分）编排。

### 数据驱动的活动系统

#### Q1：介绍一下你负责的活动系统

活动系统是一个**数据驱动**的局外系统，通过策划配置表 + 服务器下发数据实现：

- **配置表**：定义活动模板，包括活动类型、开启时间、解锁条件、任务/进度规则、奖励内容。
- **服务器下发数据**：玩家维度的活动实例数据，如已开启活动列表、当前进度、已领取奖励、活动状态。
- 客户端负责：活动开启判断、条件校验、进度更新、奖励领取入口与表现。

#### Q2：“数据驱动”具体指什么？为什么不用硬编码？

- 数据驱动指**行为由配置数据决定**，代码只实现通用的活动流程，不同活动通过换配置生成，而不是为每个活动写一套 if-else 和界面。
- 好处：策划可以独立配置新活动、复用到客户端无需改代码（配合热更甚至不发版）、减少重复逻辑、易于扩展活动类型。
- 代价：配置校验和容错要做好，配置错误要在策划工具/启动期就报出来，而不是线上崩溃。

#### Q3：活动系统怎么判断“能否开启”和“能否领取”？

- **能否开启**：结合活动配置的开启时间 + 玩家等级/章节等前置条件 + 服务器下发状态，三重校验；客户端只做展示和预检查，最终以服务器为准。
- **能否领取**：校验进度是否达标、是否已领取、背包/资源是否已满等。客户端预检查用于按钮置灰，真正领取要发请求由服务器裁决。
- 关键原则：**客户端校验只做体验，服务器校验才是权威**，防止篡改。

#### Q4：活动时间和倒计时怎么处理？

- 用服务器时间戳，不用本地时间，避免玩家改系统时间。
- 登录或请求时估算服务器时间偏移（结合 RTT），展示倒计时用“活动结束时间 - 当前估算服务器时间”。
- 活动开始/结束的切换用定时器或服务器推送通知，跨天/时区只在展示本地日期时处理。

#### Q5：如果一个活动有多种类型（签到、累计充值、任务、兑换），代码怎么组织？

- 抽象出统一的活动基类/接口（开启、刷新、领取、倒计时），每种类型实现自己的规则，用**工厂 + 活动类型枚举**创建。
- 通用部分（活动列表、红点、时间刷新）放在框架层，差异部分（具体进度规则、界面）由子类/配置驱动。
- 避免用巨大的 `switch` 把所有活动写在一个类里。

#### Q6：活动进度是怎么更新的？

- 服务器下发权威进度，客户端收到协议或推送后更新活动 Model。
- 局内行为（如通关、击杀）产生事件，活动系统监听并刷新进度显示；但真正进度变更由服务器确认，避免客户端自增导致不一致。
- 进度刷新要做**合并/节流**，避免高频事件导致 UI 频繁重建。

### 事件机制解耦局外模块

#### Q1：活动系统为什么要用事件解耦？

- 活动系统需要依赖资源、任务、成长等多个局外模块的状态，如果直接互相引用会形成网状依赖，难以维护和测试。
- 用事件（发布-订阅）后，活动系统只关心“发生了什么事”（如资源变化、达到等级），各模块互不直接依赖，符合开闭原则。

#### Q2：事件系统怎么设计？用什么数据结构？

- 简单实现：`Dictionary<事件类型, List<委托>>`，注册/反注册/派发。
- 更好的是类型安全事件：`EventBus.Subscribe<LevelUpEvent>(handler)`，避免字符串/枚举 key 和 `object` 装箱。
- 注意点：派发时要防止遍历过程中修改订阅列表（复制一份或用安全遍历）；要管理订阅生命周期，防止泄漏。
- 全局事件总线会隐藏依赖，应限制在局外模块间使用，不要滥用成“什么都发事件”。

#### Q3：事件是同步还是异步派发？

- 默认同步，保证同一帧内状态一致、顺序可控。
- 回调里不要做耗时操作（如大资源加载），否则阻塞派发方，应转成异步或延迟到统一时机处理。
- 如果一个事件触发另一个事件，要注意**递归/循环触发**和**通知风暴**。

### UniTask 异步结算流程

#### Q1：为什么用 UniTask 而不是 Unity 协程或 C# Task？

- Unity 原生协程：基于 `IEnumerator` + `yield`，无法返回值、难以取消、异常处理弱、大量协程有 GC 开销。
- `System.Threading.Tasks.Task`：多线程模型，回主线程需要额外处理，不符合 Unity 单线程 API 使用习惯。
- **UniTask**：基于 `ValueTask` 实现，低 GC、支持 `async/await`、能返回值、能取消、能 `await` Unity 的 `AsyncOperation`/`YieldInstruction`，非常适合 Unity 主线程异步。

#### Q2：结算流程为什么要拆成多个模块？

- 关卡结算包含：**结果判定 → 奖励计算 → 数据更新 → 表现触发**，每一步职责不同、执行时机不同。
- 拆开后每个模块单一职责、可独立测试、可复用（不同玩法共用结算流程），也便于在任意步骤插入埋点、错误处理。
- 用 UniTask 串成一条可组合的异步流水线，逻辑清晰。

#### Q3：结算流程具体怎么串起来的？举个例子。

大致流程：

```text
关卡结束
  ↓
结果判定（成功/失败、星级、特殊条件）
  ↓
奖励计算（基础奖励 + 活动加成 + 首通/翻倍）
  ↓
数据更新（本地预表现 + 请求服务器确认）
  ↓
表现触发（结算动画、飘分、奖励弹窗）
  ↓
流程结束，清理资源与状态
```

用 UniTask 大致是：

```csharp
async UniTaskVoid SettleAsync(CancellationToken ct)
{
    var result = await JudgeResultAsync(ct);
    var rewards = await CalcRewardAsync(result, ct);
    await UpdateDataAsync(result, rewards, ct);
    await PlaySettleViewAsync(result, rewards, ct);
}
```

#### Q4：结算过程中玩家点了返回/断线怎么办？

- 用 `CancellationToken` 取消整条流程，避免已经离开关卡还继续跑结算。
- 关键的数据更新（如奖励入账）必须发服务器请求，客户端取消的是**表现**，不能取消服务器的权威数据变更。
- 重新进入时要能根据服务器状态恢复，而不是重复结算。

#### Q5：UniTask 有 GC 吗？怎么降低？

- UniTask 基于结构体/池化，正常情况下几乎不产生 GC，但异常、装箱、闭包捕获、`async` 状态机本身仍可能分配。
- 优化：避免在 async 方法里捕获大量局部变量、避免在热路径 `await` 中分配、用 `UniTaskVoid` 表示 fire-and-forget、复用时注意 `CancellationToken` 释放（`CancellationTokenSource` 要 Dispose）。

#### Q6：`UniTaskVoid` 和 `UniTask` 区别？

- `UniTask` 可以被 `await` 并等待完成；`UniTaskVoid` 用于不需要等待的即发即弃场景，类似 `async void`。
- `UniTaskVoid` 的异常需要在内部自己捕获，否则可能丢失或被统一处理器吞掉，适合入口方法（如按钮事件）。

### CancellationToken 生命周期管理

#### Q1：CancellationToken 在你的项目里解决什么问题？

- 结算流程、资源加载、界面打开等异步任务，在对象销毁或界面关闭后仍可能继续执行，导致**回调到已销毁对象、状态异常、重复执行**。
- 用 `CancellationToken`（配合 `CancellationTokenSource`）在生命周期结束时统一取消，保证异步流程不会泄漏到下一状态。

#### Q2：怎么避免“重复执行”和“状态异常”？

- 每次进入结算创建一个 `CancellationTokenSource`，流程结束或界面销毁时 `Cancel()` 并 `Dispose()`。
- 流程开始前做状态检查（如已经结算过就直接返回），用标记位或状态机防止重入。
- 所有 `await` 的异步步骤都传入 token，取消后立即退出，不再触发后续表现和回调。

#### Q3：CancellationTokenSource 怎么管理？容易出什么问题？

- `CancellationTokenSource` 实现了 `IDisposable`，**必须 Dispose**，否则会泄漏内部注册（尤其关联 token、定时器）。
- 常见错误：`Cancel` 后没 Dispose；多个流程共用一个 CTS 导致互相影响；把一个 token 长期保存却在别处 Cancel。
- 通常做法：每个生命周期（页面、关卡）持有自己的 CTS，`OnDestroy`/流程结束时统一释放；需要的话用 `CancellationTokenSource.CreateLinkedTokenSource` 组合多个取消源。

#### Q4：`IsCancellationRequested` 和 `ThrowIfCancellationRequested` 区别？

- `IsCancellationRequested` 是一个 bool 属性，用于手动判断、优雅收尾。
- `ThrowIfCancellationRequested()` 已取消时抛出 `OperationCanceledException`，让 `await` 链路直接中断，适合不需要额外清理的场景。
- UniTask 中通常直接让 token 参与 `await`，取消时抛异常并在外层捕获处理。

### 序列帧动画 UV 偏移优化

#### Q1：原来的序列帧动画是怎么做的？有什么问题？

- 原始做法：把序列帧切成多张 `Sprite`，每帧给 `Image.sprite` 赋值切换，或用 `Animator` 逐帧切 Sprite。
- 问题：频繁切换 Sprite 引用会打断 UGUI 合批、产生额外 SetPass/Draw Call；大量 `Sprite` 资源常驻内存；每帧改变引用也可能触发 UI 重建，性能开销大。

#### Q2：UV 偏移图集滚动播放怎么实现？

- 把整段序列帧打到一个图集/贴图上，用一张 `Image`，通过修改材质的 **UV 偏移和缩放**（`Material.SetTextureOffset` / 自定义 Shader）来显示第 i 帧区域。
- 本质是让一张贴图“滚动”，不需要切换 Sprite 引用，Draw Call 和材质切换都减少。

#### Q3：具体怎么算 UV？

- 假设图集为 `rows × cols` 帧，第 `i` 帧的 UV 缩放为 `(1/cols, 1/rows)`，偏移为 `(col * 1/cols, row * 1/rows)`。
- 注意图片上下方向与 UV 原点（Unity 默认左下角）的差异，图集行序可能要翻转。
- 用 `_MainTex_ST` 或自定义 Shader 的 UV 参数控制，Shader 里对 UV 做 `uv * scale + offset`。

#### Q4：为什么这样能减少开销？

- 不合批的主要原因是**不同材质/纹理来回切换**。固定一张贴图 + 一个材质，UI 元素可以合批，Draw Call 显著减少。
- 不再逐帧改 `sprite` 引用，避免了 UI 顶点/批次重建和资源引用切换开销。
- 内存上只需一张图集，不用保留 N 个 Sprite 对象。

#### Q5：这样做的缺点或限制？

- 需要序列帧尺寸规则、能打进图集；图集过大可能超出纹理尺寸或压缩质量下降。
- Shader 需要支持自定义 UV，部分需要 SRP Batcher / UGUI 合批兼容。
- 对非规则、带独立图层的特效表现不如逐帧 Sprite 灵活。
- 需要自己控制帧率（用计时器或 Animator 的动画事件驱动 UV 变化）。

### 结算资源加载优化

#### Q1：结算阶段为什么卡顿和黑屏？

- 结算时集中加载大量资源（奖励图标、特效、界面、音效），一次性同步加载会阻塞主线程，导致掉帧甚至卡住。
- 网络请求 + 资源加载同时进行，且没有预加载，玩家看到的是空白/黑屏。
- 资源加载完成后集中实例化，造成瞬时峰值。

#### Q2：你的优化方案是什么？

- **资源预加载**：在进入结算前的空闲时机（如关卡即将结束、加载进度界面）提前异步加载结算所需资源。
- **分帧加载**：把批量加载拆到多帧，每帧限定加载数量，避免单帧阻塞。
- **生命周期管理**：用引用计数管理资源的加载/释放，结算结束及时卸载不再使用的资源，避免内存持续增长。

#### Q3：分帧加载怎么实现？会不会导致加载总时间变长？

- 用协程/UniTask，每帧 `yield` 后加载固定数量资源，或按加载耗时预算（如每帧 2ms）来控制。
- 总时间可能略微增加，但**峰值卡顿消除、体验平滑**，而且配合预加载，玩家感知不到。
- 要限制并发数，避免同时发起过多异步加载造成 IO 和内存峰值（见热更部分并发限流）。

#### Q4：预加载的资源什么时候释放？

- 用引用计数：谁引用谁加一，释放减一，归零时才真正卸载。
- 场景切换、页面关闭时统一释放该页面持有的资源。
- 常驻资源（如通用 UI 图集、字体）不参与频繁加载卸载，单独管理。

#### Q5：怎么衡量优化效果？

- 用 Profiler / UWA 看：结算阶段 CPU 峰值、GC Alloc、主线程耗时、Draw Call、内存。
- 关注“最长单帧”和“进入结算耗时”，而不只是平均帧率。
- 对比优化前后的黑屏时长、卡顿帧数和峰值内存，给出具体数字。

### Cocos Creator + TypeScript

#### Q1：Cocos Creator 和 Unity 的区别？为什么用 Cocos？

- Cocos Creator 使用 TypeScript/JavaScript 作为脚本语言，Unity 使用 C#；Cocos 更轻量、包体小、H5/小游戏方向生态更好，适合 SLG 这类 UI 重、跨端需求多的项目。
- Unity 工具链、3D 能力和社区插件更成熟，适合中重度 3D 游戏。
- 共同点：节点/组件模型、场景/预制体、资源管理、生命周期回调（`onLoad/start/update/onDestroy`）思路相通，所以能较快迁移。

#### Q2：TypeScript 相比 JavaScript 有什么好处？

- 静态类型检查，编译期发现类型错误，重构和多人协作更安全。
- 支持接口、泛型、枚举、访问修饰符，代码组织更规范。
- 注意：TS 的类型在运行时会被擦除，运行时错误仍需额外校验（如协议数据校验）。

#### Q3：Cocos 里的异步和资源加载怎么做？

- 用 `Promise` / `async-await` 处理异步；资源用资源的加载接口（`resources.load`、Bundle 加载）配合回调或 Promise 封装。
- 需要管理加载失败、进度、并发和释放（`assetManager.releaseAsset`）。

### MVC 客户端框架

#### Q1：介绍一下你们 SLG 客户端的 MVC 框架

- **Model**：保存业务数据（建筑、资源、英雄等状态）和数据访问接口，不直接操作 UI。
- **View**：负责界面显示、输入和生命周期，不决定业务规则。
- **Controller/Presenter**：协调输入、Service 调用、Model 更新和 View 表现。
- 补充 **NetworkHandler**：协议编解码、请求响应匹配、服务器 Push 分发。
- 补充 **Service**：封装建筑升级、资源结算、招募等业务流程，避免 Controller 膨胀。

#### Q2：为什么用 MVC 而不是 MVVM？区别是什么？

- MVC 强调 Controller 协调流程，MVVM 强调 View 与 ViewModel 的**数据绑定**。
- MVVM 减少手动刷新代码，但绑定生命周期、循环更新和调试更复杂；SLG 界面多、交互重，MVC 更直接可控。
- 两者可以结合，实际项目里关键是用好分层，不要纠结名字。

#### Q3：Model 数据变了，View 怎么知道要刷新？

- Model 变化时发类型安全事件，View 订阅后刷新。
- 跨模块通信用领域事件/消息总线，但要明确事件类型、发布者和订阅者，限制全局总线滥用。
- 同一帧内多次更新 Model 时可以**合并刷新**（脏标记/刷新队列），在统一时机（如帧末）刷新 View。

#### Q4：数据先到、界面还没创建怎么办？

- Model 先更新数据，不依赖 View 是否存在。
- View 创建时主动读取 Model 当前完整状态初始化。
- View 订阅事件后只接收**后续**变化，避免漏掉已到达的数据或重复刷新。

#### Q5：界面销毁了但事件还在触发怎么办？

- 订阅时保存取消句柄，在 `onDestroy`/页面生命周期结束时注销。
- 避免静态事件长期持有 View 引用。
- 防止页面重复打开造成重复订阅（一次变化多次刷新）。

### 协议解析、状态同步与异常校验

#### Q1：客户端和服务器怎么通信？协议长什么样？

- 通常用 ProtoBuf/自定义二进制协议，包结构包含：消息 ID、长度、序列号/请求 ID、payload。
- 客户端把协议解析成数据对象，交给 NetworkHandler 分发到对应模块。
- 服务器是权威端，客户端只做表现和预检查。

#### Q2：状态同步里客户端扮演什么角色？

- 客户端发送操作请求（建造、升级、招募），服务器校验并返回权威结果或 Push 状态变化。
- 客户端用服务器返回的数据更新 Model，驱动 UI，而不是自己算最终结果。
- 客户端可以做预表现（如立即播放建造动画），但失败时回滚。

#### Q3：怎么处理“响应和 Push 乱序”？

- 用**版本号/序列号**判断数据新旧，旧数据丢弃。
- Push 可能先于请求响应到达，所以不能假设响应一定先到；以版本较高的状态为准。
- 请求带**请求 ID**，即使重发也能幂等匹配，避免重复处理。

#### Q4：异常数据校验都有哪些？

- 类型/范围校验：数值是否合法、枚举是否越界。
- 引用校验：建筑引用的配置 ID 是否存在、英雄 ID 是否合法。
- 状态校验：是否满足前置条件（等级、资源、队列）。
- 空值/缺字段校验：协议缺字段不能直接崩溃，要有默认值和容错。
- 目的：防止配置错误或服务器异常导致客户端崩溃，至少做到不闪退、可降级显示。

#### Q5：收到非法或未知协议怎么办？

- 未知消息 ID 直接忽略并记录日志，不抛异常。
- 字段缺失用默认值兜底，关键数据缺失则跳过该条更新并上报。
- 做好协议版本兼容，老客户端收到新字段要能忽略。

### UI 刷新与对象复用

#### Q1：你是怎么优化 UI 刷新的？

- 列表虚拟化：固定数量的 Item + 复用，滑动时换数据而不是创建/销毁。
- 脏标记合并：同一帧内多次数据变化只刷新一次。
- 只更新变化字段：避免无意义的 `setText`、换图、触发 Layout 重建。
- 减少频繁启停的复杂 Layout、Mask、大面积透明节点。

#### Q2：对象复用（对象池）怎么设计？

- 空闲队列 + 活动集合 + 创建策略 + 容量上限。
- 获取时优先从空闲队列取，没有则按策略扩容或排队。
- 归还时重置状态：位置、激活、动画、事件订阅、临时数据，防止脏数据。
- 不是所有对象都适合池化，高频创建销毁且结构相近的才值得。

#### Q3：频繁打开关闭界面有什么开销？

- 界面创建/销毁涉及节点树、组件初始化、资源加载，开销大。
- 优化：界面缓存复用、隐藏而非销毁、资源引用计数管理、避免每次打开都重新加载图集。
- 但缓存太多会占内存，要权衡，按界面使用频率决定是否常驻。

#### Q4：怎么定位 UI 性能瓶颈？

- 用 Profiler / Frame Debugger 看瓶颈来自脚本、布局重建、顶点重建、批次变化还是 Overdraw。
- 检查是否有无效的 Raycast Target、过大透明区域、频繁 ContentSizeFitter。
- 合批方面看图集和材质是否统一，Draw Call 是否异常。

## 四、多人联机 RPG Demo

### Mirror 分层设计与状态同步

#### Q1：为什么参考 Mirror 的“分层设计”？你自己实现了哪些部分？

- Mirror 把网络分成：**传输层**（Transport，负责收发字节）、**连接/通道层**、**消息层**（消息类型、序列化）、**同步层**（NetworkBehaviour、SyncVar、RPC）。
- 我参考这种分层，自己实现了传输层、消息序列化、状态同步和断线重连，**不是直接用 Mirror**，要能说清自研和参考的边界。
- 分层的价值：传输方式和同步逻辑解耦，替换底层（UDP/TCP/WebSocket）不影响上层。

#### Q2：状态同步和帧同步的区别？

- **状态同步**：服务器计算权威状态并同步给客户端，客户端只负责表现和预测；状态量大但逻辑简单、易反作弊。
- **帧同步**：只同步输入，各客户端按相同帧序执行相同逻辑得到相同结果；带宽小但要求确定性、难以反作弊。
- RPG 逻辑复杂、实体多，本项目用状态同步更适合。

#### Q3：状态同步具体同步哪些数据？

- 玩家位置、朝向、动画状态、血量等关键状态；场景对象的状态。
- 用**差量**和**变化频率**控制带宽：变化快的用高频插值，变化慢的用低频或按需同步。
- 客户端收到状态后用插值/平滑（如位置插值）避免瞬移。

#### Q4：客户端预测和服务器校正怎么做？

- 本地玩家操作先本地执行（预测），减少操作延迟。
- 服务器权威状态回来后，对比预测结果；不一致则校正（插值回正或回滚重演）。
- 校正要平滑，否则表现为瞬移。

#### Q5：网络线程和 Unity 主线程怎么交互？

- 网络线程收到消息不能直接操作 Unity 对象（Unity API 非线程安全）。
- 用线程安全队列（如 `ConcurrentQueue`）把消息传给主线程，主线程在固定时机消费。
- 每帧限制处理的消息数量，避免网络突发阻塞渲染。

### 全量快照断线重连

#### Q1：断线重连的整体流程？

1. 通过心跳/超时检测连接断开。
2. 用退避重连，重新认证，恢复会话 ID。
3. 服务器下发当前玩家的**全量快照**（位置、状态、血量等）。
4. 客户端用快照覆盖本地状态，恢复 UI、输入、表现。
5. 处理重连期间的未完成请求，用请求 ID 保证幂等。

#### Q2：为什么用“全量快照”而不是差量或重放？

- 本项目 Demo 规模较小，全量快照实现简单、恢复可靠，不用维护差量日志。
- 代价是状态大时带宽高，所以正式项目通常会“**定期快照 + 之后输入/增量**”而不是每次全量。
- 取舍：简单可靠 vs 带宽成本。

#### Q3：全量快照包含什么？不包含什么？

- 包含重建逻辑所需的数据：实体 ID、位置、朝向、状态、血量。
- 不包含纯表现数据：特效、音效、临时粒子，这些由客户端根据逻辑状态自己生成。

#### Q4：重连后如何避免重复触发奖励/音效？

- 快照恢复只重建逻辑状态，不重放一次性副作用。
- 副作用（奖励、音效）由“状态变化”驱动而不是“重连事件”驱动，恢复时对比新旧状态，只有真正变化才触发。

#### Q5：如何识别断线并触发重连？

- 心跳超时 + 连接状态机；客户端定时发心跳，超过 N 次未收到响应判定掉线。
- 用退避策略（如 1s、2s、4s）避免频繁重连造成服务器压力，设置最大重试次数。

### 基于 UDP 的可靠传输层

#### Q1：为什么用 UDP 而不是 TCP？UDP 有什么问题？

- UDP 无连接、无重传、无有序保证，延迟低、不会被队头阻塞，适合实时游戏。
- 但需要自己实现**可靠、有序、去重、拥塞控制**，否则丢包就丢数据。
- TCP 保证可靠有序，但队头阻塞导致延迟抖动不适合实时场景。

#### Q2：你的可靠传输层实现了哪些机制？

- **序列号**：每个包编号，判断顺序和重复。
- **确认应答（ACK）**：接收方确认已收包；可用 ACK 位图一次确认多个历史包。
- **超时检测（RTO）**：根据 RTT 动态估算超时时间，超时触发重传。
- **重传**：未确认包重发，配合退避策略，超过次数判定断线。

#### Q3：怎么处理丢包、乱序和重复包？

- 收到包先做序列号校验：重复包直接丢弃。
- 乱序包放入接收缓冲区，等缺失包补齐后按序交付。
- 可靠消息等待重传；可丢弃的实时消息可以用新数据覆盖旧数据。

#### Q4：序列号回绕怎么处理？

- 无符号整数会回绕，不能直接用大小比较。
- 用差值比较或半区间判定：若两序列号差值的绝对值小于一半范围，则认为是最近邻关系。
- 常见做法：`if ((int)(a - b) > 0)` 之类利用补码差值判断。

#### Q5：RTO 怎么估算？

- 参考 TCP：`SRTT = 平滑 RTT`、`RTTVAR = RTT 波动`，`RTO = SRTT + 4 * RTTVAR`。
- 固定 RTO 只适合特定测试环境，正式实现应动态估算并设上下限（防抖）。

#### Q6：快速重传和拥塞控制？

- 快速重传：收到重复 ACK 或检测到 ACK 缺口时立即重传，不等 RTO。
- UDP 没有内置拥塞控制，自研可靠 UDP 仍需限制发送窗口、重传速率和带宽，避免丢包时放大拥塞。

#### Q7：哪些消息需要可靠，哪些可以不可靠？

- 可靠：登录、购买、关键指令、状态变更。
- 不可靠：高频位置/朝向更新、表现类消息（丢了下一帧就补上）。
- 通常设计多个通道：可靠有序、可靠无序、不可靠。

### 自动取消订阅的 EventBus

#### Q1：你的 EventBus 是怎么实现自动取消订阅的？

- 订阅时返回一个 `IDisposable`/取消句柄，或把订阅绑定到对象的生命周期哨兵节点。
- 对象销毁时，哨兵节点触发，自动取消它名下的所有订阅。
- 内核是“订阅者 → 订阅列表”的映射，销毁时批量移除。

#### Q2：为什么需要自动取消订阅？

- 手动管理订阅容易漏：对象销毁后事件回调仍触发，导致空引用、逻辑错乱或内存泄漏（事件持有对象强引用）。
- 自动管理减少人为遗漏，尤其是 UI 页面频繁创建销毁的场景。

#### Q3：“生命周期哨兵节点”是什么？

- 一个绑定到宿主对象生命周期的组件/对象，负责在宿主销毁时统一清理订阅。
- 本质是用生命周期回调（`OnDestroy`）做资源回收，避免手动到处写注销代码。

#### Q4：事件系统有什么坑？

- 遍历时修改订阅列表：派发前复制列表或用安全遍历。
- 循环触发/通知风暴：A 事件触发 B，B 又触发 A；需限制或检测。
- 全局事件隐藏依赖：过度使用会让调用链难以追踪。
- 类型安全：避免 `object` 参数和字符串 key，减少装箱和运行时错误。

### 行为树与 Blackboard

#### Q1：为什么用行为树而不是状态机？

- 状态机适合状态少、转换明确的逻辑；状态一多就状态爆炸、连线混乱。
- 行为树把决策拆成可复用的节点（Sequence/Selector/Decorator），层级清晰、易扩展、易复用。
- 复杂角色常用“层次状态机 + 行为树”组合，而不是二选一。

#### Q2：行为树节点有哪些类型？

- **Composite**：Sequence（依次执行，遇 Fail/Running 停止，全 Success 才成功）、Selector（依次执行，遇 Success/Running 停止，全 Fail 才失败）、Parallel。
- **Decorator**：包装单个子节点，实现条件、反转、重复、冷却、超时。
- **Leaf/Action/Condition**：具体行为（移动、攻击）和条件判断。
- 节点返回 `Success`/`Failure`/`Running`。

#### Q3：Blackboard 是干什么的？

- 分离**行为逻辑**和**运行时数据**：行为树只描述决策结构，感知、目标、路径等共享数据放 Blackboard。
- 多个 NPC 共享同一棵行为树结构，但各自持有独立 Blackboard，避免数据串扰。
- Blackboard 应类型安全访问，避免字符串 key 和 `object` 装箱。

#### Q4：行为树性能怎么优化？

- 不要每帧遍历整棵树，只 Tick 当前活动分支（`Running` 路径）。
- 按距离分级、远处 NPC 降频、分帧执行、事件驱动唤醒。
- 复杂行为拆成独立服务（寻路、感知、战斗），行为树只做编排。

### A* 寻路

#### Q1：A* 的原理？

- 在 Dijkstra 基础上加启发函数：`F = G + H`，`G` 是起点到当前的实际代价，`H` 是到终点的估计代价。
- Open List（小根堆）取最小 F 节点，Closed Set 记录已处理节点，维护 GScore 和父节点。
- 小根堆优化后常见复杂度约 `O((V + E) log V)`。

#### Q2：启发函数怎么选？

- 曼哈顿距离适合四方向网格；允许斜向用对角/Octile 距离；欧几里得距离是否可采纳取决于移动规则和边权。
- H 必须**可采纳**（不高估），否则 A* 不保证最优。

#### Q3：A* 有哪些优化？

- 小根堆替代线性查找。
- 路径缓存、同目标请求合并。
- 分帧搜索、请求队列，避免阻塞主线程。
- 分层寻路、双向 A*、Jump Point Search、路径平滑（漏斗算法）。
- 远处 NPC 降频，动态障碍只重算受影响路径。

#### Q4：为什么保证结果确定？

- F 相同时固定 tie-break 规则（如比较 H、节点编号或插入顺序），避免不同运行顺序产生不同路径。

#### Q5：动态障碍怎么处理？

- 局部避障 + 定期重规划；或更新导航数据后重新寻路。
- 全图重算代价高，通常只重算受影响区域。

## 五、HybridCLR 热更新与启动方案

### 资源热更 manifest + MD5

#### Q1：资源热更新的整体流程？

- 服务器维护 `manifest.json`，列出所有资源的路径、版本、**MD5** 和分包信息。
- 客户端启动时拉取最新 manifest，和本地 manifest 对比，找出**新增/修改**的资源。
- 只下载差异资源（增量更新），校验 MD5 后写入本地缓存，更新本地 manifest。

#### Q2：为什么要用 MD5？

- 用 MD5 作为资源内容的指纹，判断资源是否变化：内容变则 MD5 变。
- 下载后重新计算 MD5 与 manifest 对比，校验文件完整性，防止下载损坏或被篡改（安全场景应配合签名，MD5 本身可碰撞）。

#### Q3：增量更新怎么判断哪些要下载？

- 对比新旧 manifest：本地没有的（新增）和 MD5 不同的（修改）都要下载；本地多余的可清理。
- 相比全量下载，显著减少流量和更新时间。

#### Q4：manifest 本身怎么更新？（鸡生蛋问题）

- manifest 用固定的 URL 拉取（带时间戳/版本参数防缓存），或用一个极小的版本号文件先判断 manifest 是否需要更新。
- 保证客户端一定能拿到最新清单。

#### Q5：MD5 计算大文件会不会卡？

- 大文件分块计算、放到子线程/异步计算，避免阻塞主线程。
- 可以用文件的 size + 修改时间先做快速筛选，MD5 做二次精确校验。

### 首包与分包资源

#### Q1：什么是首包和分包？

- **首包**：随安装包一起发布的资源，玩家安装后即可进入游戏（登录、主界面、新手引导等必需资源）。
- **分包**：不随包体发布、按需下载的资源（不同玩法、不同关卡、高清资源等），减小初始包体、加快上架和下载。

#### Q2：怎么划分哪些进首包、哪些进分包？

- 首包放“进游戏必需 + 高频使用”的资源；其余按功能模块/玩法分到分包。
- 目标是启动快、包体小、首次进入某玩法及时下载。
- 需要和策划/运营权衡，避免把关键资源放分包导致首次体验差。

#### Q3：玩法进入前资源没下载完怎么办？

- 进入前检查所需分包是否就绪，未就绪则先下载（进度界面），或边玩边异步下载。
- 下载失败要有重试和降级方案（占位资源）。

### 断点续传与失败回滚

#### Q1：断点续传怎么实现？

- 下载时用 **Range 请求**（`Range: bytes=start-`）从已下载位置继续，而不是从头下载。
- 本地记录已下载的临时文件和偏移，中断后重新请求时带上偏移。
- 全部下载完并校验 MD5 后再正式启用，避免用不完整文件。

#### Q2：下载失败/中断怎么回滚？

- 下载到临时目录，校验通过前不替换正式资源，失败时删除临时文件。
- 保留旧的可用资源，更新失败时回退到旧版本，保证游戏仍能启动。
- 用“版本目录 + 原子切换”避免更新到一半崩溃导致资源损坏。

#### Q3：怎么校验更新完整性？

- 每个文件校验 MD5，整体用文件清单数量/大小校验。
- 关键配置或代码程序集可增加签名校验。

#### Q4：更新过程中断线/秒退怎么办？

- 记录更新进度，下次启动从断点继续或回滚到旧版本。
- 更新流程要幂等，重复执行不会破坏已有资源。

### HybridCLR 原理

#### Q1：HybridCLR 是什么？原理是什么？

- HybridCLR 是一个**基于 IL2CPP 的 C# 热更新方案**，让 IL2CPP（AOT）环境下也能运行动态加载的 C# 程序集。
- 核心是在 IL2CPP 运行时里补充了一套 **解释器**，热更程序集以 DLL 形式下发，运行时用解释器执行其中的方法。
- 与 xLua 不同，HybridCLR 热更的是 **C# 原生代码**，不需要把逻辑翻译成 Lua，开发体验和性能更接近原生。

#### Q2：HybridCLR 和 xLua 的区别与取舍？

| 维度 | HybridCLR | xLua |
| --- | --- | --- |
| 热更语言 | C# | Lua |
| 运行方式 | AOT + 解释器 | Lua 虚拟机 |
| 性能 | 接近原生（AOT 部分原生，热更部分解释） | 跨语言调用有开销 |
| 开发体验 | 直接用 C#，无跨语言 | 需写 Lua，C#/Lua 互调 |
| 兼容性 | 需处理 AOT 泛型、裁剪 | 需生成绑定代码 |
| 成熟度/生态 | 较新，社区活跃 | 老牌，项目多 |

- 取舍看团队技术栈和历史包袱：新项目、想统一 C# 可优先 HybridCLR；已有大量 Lua 逻辑则继续 xLua。

#### Q3：热更程序集怎么划分？

- **AOT 程序集**：不能热更、随包发布的基础代码（引擎、第三方库、框架底层、启动代码）。
- **热更程序集**：需要迭代的业务逻辑（玩法、活动、UI），以 DLL 形式下发。
- 划分原则：稳定不变的下沉到 AOT，频繁迭代的放热更；AOT 程序集不能被热更程序集反向依赖，否则无法更新。

#### Q4：热更程序集怎么加载运行？

- 下载校验 DLL 后，用 `Assembly.Load(byte[])` 动态加载，再通过反射或预先约定好的入口调用其中的类型和方法。
- 需要注册/替换入口，让启动流程走到热更程序集里的逻辑。
- 加载失败要有回退（用内置版本）。

---

### AOT 泛型问题与 IL2CPP

#### Q1：什么是 AOT 泛型问题？

- IL2CPP 是 AOT 编译，泛型实例在**编译期确定**。如果某个泛型类型/方法在 AOT 程序集里没有对应实例，运行时动态调用时就会报 `ExecutionEngineException` 或找不到方法。
- 例如热更代码里用了 `List<SomeNewType>`，而 AOT 里没为 `SomeNewType` 生成过这个实例，就会出问题。

#### Q2：怎么解决 AOT 泛型问题？

- **补充 AOT 泛型元数据**：在 AOT 程序集里显式“引用”需要的泛型实例（如一个专门的 `AOTGenericReferences` 类里声明这些类型），让 IL2CPP 提前生成。
- HybridCLR 提供了 AOT 泛型收集/补充工具，扫描热更代码用到的泛型，自动生成引用代码。
- **封装 AOT 工具类**：把容易出现泛型问题的操作（如特定泛型反射）包装成 AOT 中已有的方法。

#### Q3：什么是 link.xml？为什么需要防裁剪？

- IL2CPP 构建时会做**代码裁剪（Managed Stripping）**，删掉没用到的类型和方法以减小包体。
- 但反射调用的类型、热更代码依赖的类型在静态分析下“没被引用”，可能被误裁，导致运行时找不到。
- `link.xml` 用来告诉裁剪器**保留**指定程序集/类型/方法，防止被裁掉。

#### Q4：为什么热更代码在 IL2CPP 下容易出问题？

- 反射 + 泛型 + 裁剪三者叠加：反射用的类型可能被裁、泛型实例可能没生成、动态生成的 IL 不被支持。
- 需要综合 `link.xml`、AOT 泛型补充、避免运行时动态生成代码来保证稳定。

#### Q5：Mono 和 IL2CPP 的区别？

- Mono：JIT 编译，运行时编译 IL，支持反射和动态代码方便，但性能较低、部分平台（如 iOS）不允许 JIT。
- IL2CPP：提前把 IL 转成 C++ 再编译为原生代码，性能好、跨平台，但 AOT 限制反射和泛型动态实例化。
- 热更方案必须考虑 IL2CPP 的限制，这也是 HybridCLR 存在的原因。

### 加载性能优化

#### Q1：分帧加载、并发限流、引用计数分别解决什么？

- **分帧加载**：把批量加载拆到多帧，避免单帧阻塞主线程。
- **并发限流**：限制同时进行的异步加载数，避免 IO/内存峰值和加载队列拥塞。
- **引用计数**：管理资源生命周期，谁用谁加一，释放减一，归零卸载，避免重复加载和内存泄漏。

#### Q2：启动耗时怎么优化？

- 减少首包同步加载、关键资源预加载、分帧初始化。
- 拆分启动阶段，先进入可交互界面，其余异步加载。
- 用 Profiler 定位启动各阶段耗时，优化最大瓶颈。

#### Q3：怎么避免资源重复加载？

- 统一资源管理器，按资源路径/Key 缓存已加载的资源，配合引用计数，重复请求直接复用。
- 异步加载中的请求做去重，避免同一个资源同时被加载多次。

#### Q4：内存峰值怎么控制？

- 并发限流 + 及时释放 + 引用计数，避免瞬时加载大量资源。
- 大图可降分辨率或按需加载，及时卸载场景切换后不用的资源。

## 六、专业技能横向提问

### C# 语言特性

#### Q1：值类型和引用类型区别？装箱拆箱是什么？

- 值类型（struct、int 等）存栈或内联在对象里，赋值是拷贝；引用类型（class）存堆上，变量持有引用。
- 装箱：值类型转 `object`/接口时在堆上分配包装对象；拆箱：从 `object` 取回值类型。
- 游戏里频繁装箱拆箱会产生 GC，热路径要避免（如事件用 `object` 参数、非泛型集合）。

#### Q2：`struct` 和 `class` 怎么选？

- `struct` 适合小型、短生命周期、值语义的数据（向量、帧输入、配置项），避免堆分配。
- `class` 适合需要继承、引用语义、生命周期管理的对象。
- `struct` 不要太大（拷贝成本），也不要在里面放可变引用导致语义混乱。

#### Q3：委托、事件、Action/Func 区别？

- 委托是方法的引用；`Action` 无返回值，`Func` 有返回值，是内置泛型委托。
- `event` 是对委托的封装，限制外部只能 `+=`/`-=`，不能直接调用或覆盖，保证封装性。
- 事件系统底层就是委托的订阅列表。

#### Q4：GC 是什么？怎么减少 GC？

- C# 托管堆由 GC 自动回收，回收时可能造成主线程停顿（尤其大对象、频繁分配）。
- 减少方法：对象池、复用集合、避免装箱、避免闭包捕获、用 `StringBuilder`、预分配数组、用 `struct` 和 `Span`、避免每帧 `new`。

#### Q5：协程、Thread、Task、UniTask 的区别？

- 协程：Unity 主线程分帧执行，不能返回值、取消弱。
- Thread：真正多线程，不能操作 Unity API。
- Task：线程池多线程模型。
- UniTask：基于 ValueTask 的 Unity 异步方案，主线程友好、低 GC、可取消。

#### Q6：`ref`/`out`/`in` 区别？

- `ref`：传入已有变量，可读可写。
- `out`：方法内必须赋值，用于返回多个值。
- `in`：只读引用，避免大结构体拷贝。

### Unity / UGUI

#### Q1：Unity 生命周期函数执行顺序？

- `Awake → OnEnable → Start → FixedUpdate → Update → LateUpdate → OnDisable → OnDestroy`。
- `Awake` 初始化引用，`Start` 做依赖其他对象的初始化，`FixedUpdate` 处理物理，`LateUpdate` 处理跟随相机/统一刷新。

#### Q2：UGUI 合批/Draw Call 怎么优化？

- 减少 Canvas 重建范围：把频繁变化和静态 UI 拆到不同 Canvas，避免一个元素变化导致整个 Canvas 重建。
- 用图集统一材质，减少材质/纹理切换；但图集不保证一定减少 Draw Call。
- 列表虚拟化、对象池、减少 Layout/Mask/透明大面积元素和无效 Raycast Target。

#### Q3：为什么 UI 元素变一下会触发整个 Canvas 重建？

- UGUI 按 Canvas 做合批，同一 Canvas 内某元素的顶点/布局变化会导致该 Canvas 的网格重建（重建顶点和批次）。
- 拆分 Canvas + 减少布局依赖可以缩小重建范围。注意 Canvas 太多会增加批次和层级管理开销，要平衡。

#### Q4：`Image` 和 `RawImage` 区别？

- `Image` 用 Sprite，支持九宫格、填充、图集合批；`RawImage` 用 Texture，更灵活（可任意 UV、渲染纹理），但不参与图集合批。
- 序列帧用 UV 偏移时常用带自定义材质的 `Image` 或 `RawImage`。

#### Q5：AssetBundle 和 Addressables 区别？

- AssetBundle 是底层资源打包格式，需要自己管理依赖、加载、卸载和版本。
- Addressables 是官方在 AB 之上的资源管理系统，提供地址寻址、依赖管理、异步加载、远程更新和引用计数。
- 二选一看项目需求，Addressables 更省心但更重。

#### Q6：资源引用计数为什么重要？

- 同一个资源可能被多处使用，不能某处不用就卸载，否则别处变“粉红”。
- 用引用计数：加载 +1，释放 -1，归零才真正卸载；配合统一资源管理器避免重复加载。

### 热更新路线对比

#### Q1：资源热更和代码热更的区别？

- **资源热更**：更新图片、配置、Prefab 等资源，通过 manifest + MD5 增量下载，不改代码逻辑。
- **代码热更**：更新 C#/Lua 逻辑，需要 HybridCLR（C#）或 Lua 虚拟机（xLua），能修复逻辑 Bug、上新玩法而不用重新发版。

#### Q2：什么情况下热更换不了、必须发版？

- 引擎版本升级、原生插件变更、底层结构变化、AOT 程序集变更（HybridCLR 不能热更 AOT 部分）、平台审核相关政策变化。
- 新增权限、新的原生能力也要发版。

#### Q3：热更新的安全风险？

- 下载内容可能被篡改（需签名校验）、旧客户端加载不兼容逻辑、灰度/回滚机制缺失导致大面积崩溃。
- 要有版本兼容、灰度发布、回滚和监控。

### 网络开发

#### Q1：TCP 和 UDP 区别？

- TCP：面向连接、可靠、有序、有流量和拥塞控制，但有队头阻塞，延迟抖动大。
- UDP：无连接、不可靠、无序，但延迟低、无队头阻塞，需要自己实现可靠机制。
- 游戏高频实时数据用 UDP，登录/支付等关键数据可用 TCP 或 UDP 的可靠通道。

#### Q2：帧同步、状态同步、客户端预测分别是什么？

- 帧同步：同步输入，各端按相同帧序执行相同逻辑。
- 状态同步：同步权威状态，客户端表现。
- 客户端预测：本地先执行，服务器结果回来再校正，降低操作延迟。

#### Q3：断线重连要注意什么？

- 重连期间的状态保持、快照恢复、未完成请求幂等处理、避免重复副作用、平滑恢复表现。

#### Q4：心跳是干什么的？

- 检测连接存活，及时发现断线；也可用于保活 NAT 映射。
- 间隔要权衡：太频繁浪费带宽，太稀疏断线检测慢。

### 性能优化

#### Q1：Unity 性能优化一般从哪些方面入手？

- **CPU**：脚本逻辑、GC、物理、渲染提交、AI/寻路、UI 重建。
- **GPU**：Draw Call、Overdraw、Shader 复杂度、带宽、LOD/剔除。
- **内存**：资源引用计数、对象池、纹理压缩、及时卸载。
- **加载**：预加载、分帧、并发限流。
- 统一原则：**先用 Profiler 定位瓶颈，再针对性优化，优化后对比数据**。

#### Q2：Draw Call 是什么？怎么降？

- 一次 CPU 向 GPU 提交渲染命令（一次材质/网格批次）。太高会受 CPU 提交瓶颈限制。
- 降法：合批（静态/动态/GPU Instancing/SRP Batcher）、图集统一材质、减少材质切换、LOD/剔除。

#### Q3：Overdraw 怎么优化？

- Overdraw 是同一像素被多次绘制（大面积透明、叠加 UI）。
- 减少透明层叠、缩小透明区域、去无效 UI、优化粒子。

#### Q4：对象池的注意事项？

- 归还时重置状态，防止脏数据；设置容量上限；不回收正在使用的对象；管理好事件订阅和协程。

#### Q5：怎么分析 GC？

- 用 Profiler 的 GC Alloc 列定位每帧分配来源；注意字符串拼接、装箱、闭包、LINQ、`foreach` 在部分集合上的分配。
- 优化：缓存、复用、`StringBuilder`、避免热路径 LINQ。

## 七、算法与计算机基础

### Q1：手写快排 / 归并？

- 快排：选基准，partition 分区，递归；平均 `O(n log n)`，最坏 `O(n²)`，不稳定。
- 归并：分治 + 合并，稳定，`O(n log n)`，需要额外空间。

### Q2：栈和队列、链表和数组区别？

- 数组随机访问 `O(1)`，插入删除 `O(n)`；链表插入删除 `O(1)`（已知节点），随机访问 `O(n)`。
- 栈 LIFO，队列 FIFO；游戏里常用队列做消息/请求队列。

### Q3：哈希表原理？解决冲突？

- 通过哈希函数把 key 映射到桶；冲突用链地址法或开放寻址解决。
- 平均 `O(1)`，最坏 `O(n)`；`Dictionary` 遍历顺序不保证，逻辑不要依赖。

### Q4：排序稳定性有什么用？

- 稳定排序保持相等元素的相对顺序，多关键字排序时有用。

### Q5：红黑树和 AVL 树？

- 都是平衡二叉搜索树，查找/插入/删除 `O(log n)`。
- AVL 平衡更严格、查询略快、旋转多；红黑树近似平衡、更新旋转少，适合频繁增删。

## 八、图形学（GAMES101 / GAMES104）

### Q1：渲染管线大致流程？

- 应用阶段（CPU 剔除、提交）→ 几何阶段（顶点着色、图元装配、裁剪、屏幕映射）→ 光栅化（片元着色、深度测试、混合）→ 输出到屏幕。

### Q2：MVP 矩阵分别是什么？

- Model 模型变换（局部→世界）、View 视图变换（世界→相机）、Projection 投影（相机→裁剪，正交/透视）。

### Q3：光照模型？PBR 是什么？

- 简单有 Lambert 漫反射、Phong/Blinn-Phong 高光。
- PBR 基于物理：能量守恒、BRDF、金属度/粗糙度工作流，表现更真实一致。

### Q4：深度测试和透明渲染？

- 不透明物体开深度测试和写入，顺序无关；透明物体通常关深度写入、按从远到近排序、Alpha 混合。

### Q5：早深度测试（Early-Z）和剔除？

- Early-Z 在片元着色前做深度测试，剔除被遮挡片元。（HSR/Z-prepass）
- 视锥剔除、背面剔除、遮挡剔除减少提交和绘制。

### Q6：Draw Call 和 GPU 瓶颈怎么判断？

- 看 GPU 还是 CPU 受限：降低分辨率看帧率是否提升可判断 GPU 瓶颈；提交 draw call 数量看 CPU 提交瓶颈。
