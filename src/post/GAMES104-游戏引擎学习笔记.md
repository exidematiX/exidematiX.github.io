## 第 1 天：游戏引擎总体架构、数学与实时渲染基础

**当天目标**：理解一款游戏启动后，程序每一帧都做了什么；理解 3D 模型为什么能以正确位置、角度和大小显示到屏幕上。

建议投入 6-8 小时。今天不要求写复杂代码，重点是建立概念和流程感。

### 一、什么是游戏引擎

可以把游戏拆成两部分：

- **游戏内容**：角色、地图、任务、技能、剧情、UI。
- **通用能力**：显示画面、播放声音、处理键盘鼠标、计算碰撞、加载模型和贴图、播放动画。

游戏引擎主要负责第二部分。它为游戏内容提供可重复使用的基础设施。

例如，玩家按下 `W` 键让角色前进，背后并不是“一行让角色移动的代码”：

1. 输入系统发现玩家按下了 `W`。
2. 游戏逻辑判断角色应该向前移动。
3. 动画系统把角色切换到“走路”动画。
4. 物理系统检查角色是否会撞墙、是否在地面上。
5. 场景系统更新角色的位置和朝向。
6. 渲染系统把更新后的角色、地面、光照和镜头画到屏幕。
7. 音频系统可能播放脚步声。

这些事情会在极短时间内重复执行。若游戏目标帧率为 60 FPS，则每秒要重复约 60 次。

### 二、游戏主循环：引擎如何持续运行

游戏不是“运行一次后结束”的普通程序，而是一个持续循环的程序。这个循环叫作 **Game Loop（游戏主循环）**。

可以先把它理解成下面的伪代码：

```cpp
initializeEngine();

while (gameIsRunning) {
    pollInput();       // 读取键盘、鼠标、手柄等输入
    updateGameLogic(); // 更新游戏规则、角色状态、AI 等
    updatePhysics();   // 计算碰撞、重力、移动
    updateAnimation(); // 计算角色骨骼姿态和动画状态
    renderFrame();     // 生成并显示这一帧画面
}

shutdownEngine();
```

#### 1. 初始化

游戏启动时，引擎通常需要完成：

- 创建窗口；
- 初始化显卡接口和渲染设备；
- 初始化键盘、鼠标、手柄输入；
- 加载配置文件；
- 加载第一个场景、角色、贴图、音频等资源；
- 创建摄像机、光源和游戏对象。

例如，进入一个 3D 游戏的主菜单时，屏幕上已经出现了模型、背景和按钮。它们并不是临时画出来的，而是在初始化阶段从资源文件加载并组织起来的。

#### 2. 每帧更新

一帧就是屏幕显示的一张画面。

假设你的显示器是 60Hz，游戏稳定在 60 FPS，那么一帧大约只有：

```text
1 / 60 秒 = 16.67 毫秒
```

引擎需要在约 16.67ms 内完成输入处理、逻辑、物理、动画和渲染。如果超过这个时间，画面就可能卡顿。

#### 3. 关闭和资源释放

退出时需要释放资源，例如：

- 显存中的模型和贴图；
- 打开的音频设备；
- 文件句柄；
- 网络连接；
- 内存中的场景数据。

这部分看似简单，但对大型工程很重要。资源没有正确释放，可能造成内存泄漏、显存泄漏或程序崩溃。

### 三、游戏引擎的核心模块

初学时不需要记住每个模块的实现，只需要明确它们的职责和连接方式。

| 模块 | 解决的问题 | 示例 |
|---|---|---|
| 平台层 | 操作系统和硬件差异 | 创建窗口、读取鼠标 |
| 输入系统 | 玩家做了什么操作 | 按键、触屏、手柄 |
| 场景系统 | 世界里有什么东西 | 角色、树木、相机、灯光 |
| 资源系统 | 如何加载和管理文件 | 模型、贴图、音频、Shader |
| 渲染系统 | 如何把 3D 世界显示到屏幕 | 光照、阴影、材质 |
| 动画系统 | 角色如何自然地动起来 | 跑步、跳跃、攻击 |
| 物理系统 | 如何模拟运动和碰撞 | 重力、墙壁、刚体 |
| 音频系统 | 如何播放和定位声音 | 背景音乐、脚步声 |
| 脚本/逻辑系统 | 如何实现游戏规则 | 任务、技能、AI |
| 编辑器和工具链 | 如何让开发人员高效制作内容 | 场景编辑器、性能分析器 |

### 一个重要认识

游戏引擎不是单独的“渲染器”。

渲染器负责把画面显示出来，但游戏引擎还要管理世界、处理输入、运行逻辑、更新动画和物理、加载资源。渲染只是引擎中非常重要的一个系统。

### 四、3D 世界的基本组成

一个最小的 3D 场景通常包含以下对象：

- **Mesh（网格）**：模型的几何形状，例如角色、立方体、地面。
- **Texture（纹理）**：贴在模型表面的图片，例如木头、皮肤、金属。
- **Material（材质）**：定义模型表面如何反射和吸收光。
- **Light（光源）**：决定物体是否被照亮、阴影如何出现。
- **Camera（相机）**：决定玩家从哪个位置、哪个角度观察世界。
- **Game Object / Entity（游戏对象/实体）**：场景中可被管理的对象，例如角色、灯、树、子弹。

以一个角色为例：

```text
角色对象
├── Transform：位置、旋转、缩放
├── Mesh Renderer：使用哪个模型、哪个材质进行绘制
├── Animator：播放待机、走路、跑步等动画
├── Collider：用于碰撞检测
├── Rigidbody：用于物理模拟（可选）
└── Script：角色移动、攻击、生命值等逻辑
```

其中，今天最重要的是理解 `Transform` 和相机，因为它们连接了数学和渲染。

### 五、3D 坐标：如何描述物体的位置

在 2D 游戏中，位置通常写成：

```text
(x, y)
```

例如 `(100, 200)` 表示屏幕上的一个点。

在 3D 游戏中，需要多一个深度方向：

```text
(x, y, z)
```

例如：

```text
角色位置 = (3, 0, 5)
```

通常表示：

- 向右 3 个单位；
- 高度为 0；
- 向前或向后 5 个单位。

坐标轴的朝向因引擎和图形 API 而异，但经常可以暂时按下面理解：

```text
x 轴：左右
y 轴：上下
z 轴：前后
```

### 向量是什么

向量可以理解为“有方向和长度的量”。

例如：

```text
位置：playerPosition = (3, 0, 5)
移动方向：forward = (0, 0, 1)
速度：velocity = (0, 0, 4)
```

如果角色每秒向前移动 4 个单位，并且经过了 `deltaTime` 秒，那么位置更新可以近似写为：

```cpp
position = position + velocity * deltaTime;
```

`deltaTime` 表示两帧之间实际经过的时间。使用它的目的是让不同帧率下的移动速度保持一致。

例如：

- 60 FPS 时，每帧约移动 `4 * 0.0167`；
- 30 FPS 时，每帧约移动 `4 * 0.0333`。

虽然每帧移动距离不同，但一秒钟总移动距离仍接近 4 个单位。

### 六、Transform：位置、旋转和缩放

一个 3D 对象的空间状态通常由三类信息构成：

```text
Position：位置
Rotation：旋转
Scale：缩放
```

例如一棵树：

```text
位置： (10, 0, -3)
旋转： 绕 y 轴旋转 45 度
缩放： (2, 2, 2)
```

这表示树放在场景坐标 `(10, 0, -3)`，朝向斜前方，并放大两倍。

在程序和图形学中，通常用矩阵把位置、旋转、缩放组合成一个整体，这叫作 **Model Matrix（模型矩阵）**。

初学阶段不必手算 4x4 矩阵，但需要先建立这个理解：

> 矩阵是一种把顶点从一个坐标空间转换到另一个坐标空间的工具。

模型文件里的顶点通常围绕模型自身原点保存。例如一个立方体的顶点可能在：

```text
(-1, -1, -1)
( 1, -1, -1)
( 1,  1, -1)
...
```

通过模型矩阵后，它才会被放到游戏世界中的正确位置、角度和大小。

### 七、从模型到屏幕：五个坐标空间

这是今天最关键的知识之一。

一个模型顶点要显示到屏幕上，需要经过多次坐标变换：

```text
Local Space
    ↓ Model Matrix
World Space
    ↓ View Matrix
View Space
    ↓ Projection Matrix
Clip Space
    ↓ 透视除法
NDC
    ↓ 视口变换
Screen Space
```

#### 1. Local Space：局部空间

局部空间也叫模型空间。

它描述模型本身。例如，角色模型的脚底、头顶和手部坐标，都以角色自身为参考，而不是以整个游戏地图为参考。

```text
角色手部顶点：(0.3, 1.2, 0.1)
```

这个数字只是“相对角色原点”的位置。

#### 2. World Space：世界空间

世界空间是所有物体共享的游戏世界坐标系。

通过模型矩阵，把角色、树木、武器、建筑从各自局部坐标，放到同一个世界中：

```text
角色在世界坐标：(5, 0, 10)
树在世界坐标：(-3, 0, 7)
```

#### 3. View Space：观察空间

观察空间以相机为中心。

假设相机在世界坐标 `(0, 2, 10)`，朝向前方。经过 View Matrix（观察矩阵）后：

- 相机本身相当于被移动到原点；
- 世界中的其他物体会相对相机发生反向变化。

这很像拍照时相机不动、世界在相机前变化。实际计算时，也常把它理解为“让世界反向移动和旋转，以匹配相机的位置与朝向”。

#### 4. Clip Space：裁剪空间

通过 Projection Matrix（投影矩阵）后，3D 空间会被转换为适合显卡处理的裁剪空间。

投影分为两种：

- **透视投影**：近大远小，常用于 3D 游戏。
- **正交投影**：远近不改变大小，常用于 2D 游戏、地图、编辑器视图。

透视投影中，离相机越远的物体显示越小，这是现实世界中的视觉规律。

#### 5. NDC 和 Screen Space：标准化设备坐标与屏幕坐标

裁剪后，图形会经过透视除法，转为 NDC。可以简单把它理解为一个标准范围：

```text
x：-1 到 1
y：-1 到 1
z：通常在一个标准深度范围内
```

最后，再把范围映射到实际屏幕像素：

```text
(-1, -1) → 左下角
( 1,  1) → 右上角
```

例如 1920x1080 屏幕中，最终会得到类似：

```text
(960, 540)
```

这就是屏幕中心附近的像素位置。

### 八、MVP 矩阵

上面的变换通常合并成一句：

```text
MVP = Projection × View × Model
```

其中：

- `Model Matrix`：物体从局部空间放到世界空间。
- `View Matrix`：根据相机位置和方向观察世界。
- `Projection Matrix`：把 3D 场景投影到二维屏幕。

对于一个局部顶点 `localPosition`：

```text
clipPosition = Projection × View × Model × localPosition
```

为什么矩阵乘法顺序看起来是反的？

因为数学表达中右边先执行：

1. 先执行 `Model`；
2. 再执行 `View`；
3. 最后执行 `Projection`。

你当前不需要推导矩阵乘法，只要牢牢记住每个矩阵的职责。

### 九、实时渲染管线

显卡并不是直接“画一个模型”，而是按固定流程处理数据。这条流程叫作 **Rendering Pipeline（渲染管线）**。

可以把它粗略理解为：

```text
模型顶点数据
    ↓
顶点着色器
    ↓
图元装配
    ↓
光栅化
    ↓
片元着色器
    ↓
深度测试、混合
    ↓
屏幕上的最终像素
```

#### 1. 顶点数据

模型由大量顶点组成。每个顶点通常包含：

```text
位置：Position
法线：Normal
纹理坐标：UV
颜色：Color（可选）
切线：Tangent（可选）
```

例如，一个三角形需要至少三个顶点。

GPU 最终主要绘制的是三角形。复杂角色、建筑和地形，本质上都是由大量三角形构成。

#### 2. 顶点着色器 Vertex Shader

顶点着色器处理每一个顶点。

它最基础的职责是：

```text
把模型顶点从局部空间转换到裁剪空间。
```

伪代码如下：

```glsl
gl_Position = projection * view * model * localPosition;
```

这里并不是“给顶点涂颜色”。尽管名字中有 Shader，但顶点着色器最典型的职责是计算顶点位置。

#### 3. 图元装配 Primitive Assembly

GPU 根据顶点索引把顶点组成图元，最常见的图元是三角形。

例如：

```text
顶点 0、1、2 → 三角形 A
顶点 2、3、0 → 三角形 B
```

两个三角形可以组成一个矩形。

#### 4. 光栅化 Rasterization

光栅化负责确定“三角形覆盖了屏幕上的哪些像素”。

3D 三角形经过投影后落到二维屏幕上，光栅化阶段会生成许多待处理的像素候选点。这些候选点通常称为 **Fragment（片元）**。

可以把它想象为：GPU 判断一个三角形覆盖了屏幕上的哪些小格子。

#### 5. 片元着色器 Fragment Shader

片元着色器决定每个片元最终应有的颜色。

它可能会计算：

- 这个位置使用纹理的哪个颜色；
- 这个位置受到多少光照；
- 是否处于阴影中；
- 金属、粗糙表面应该如何反光；
- 是否需要透明混合。

非常简化的概念代码如下：

```glsl
finalColor = textureColor * lightIntensity;
```

真实游戏的材质计算会复杂得多，但本质仍是：根据材质、纹理、法线、光源和观察方向计算像素颜色。

#### 6. 深度测试 Depth Test

假设相机前方有一棵树，树后有一面墙。虽然墙也会被绘制，但墙被树遮住的位置不应显示出来。

深度测试会保存每个像素当前最近物体的深度：

- 新片元更近：覆盖旧颜色；
- 新片元更远：丢弃。

这就是为什么正常情况下，前面的物体能遮挡后面的物体。

### 十、CPU、GPU 与 Draw Call

游戏渲染通常由 CPU 和 GPU 协作完成。

### CPU 主要负责

- 更新游戏逻辑；
- 管理场景对象；
- 判断哪些物体需要绘制；
- 准备模型、材质和相机数据；
- 向 GPU 发出绘制命令。

### GPU 主要负责

- 执行顶点着色器；
- 光栅化三角形；
- 执行片元着色器；
- 完成深度测试、混合和最终像素输出。

CPU 发给 GPU 的一次绘制命令通常称为 **Draw Call**。

例如，要绘制：

```text
一栋建筑
十棵树
五十块石头
一个角色
```

如果每个物体都单独提交一次，就可能需要很多 Draw Call。

Draw Call 太多时，CPU 与 GPU 的通信成本可能成为性能瓶颈。因此现代引擎会通过合批、实例化等方式减少 Draw Call。今天先知道这个问题即可，后续学习渲染优化时会深入。

### 一、回顾：第一天的渲染流程

第一天学习的内容解决了一个问题：

> 如何把一个 3D 模型投影到 2D 屏幕上。

今天继续解决另一个问题：

> 模型投影到屏幕后，每个像素应该是什么颜色？

一帧画面的简化流程如下：

```text
场景中的模型、光源、相机
    ↓
顶点变换：确定模型在屏幕的什么位置
    ↓
光栅化：确定三角形覆盖哪些像素
    ↓
材质和光照计算：确定每个像素的颜色
    ↓
阴影、透明、抗锯齿、亮度映射等处理
    ↓
显示到屏幕
```

### 二、颜色和光照的基本概念

#### 1. 为什么物体能被看见

在黑暗中，即使有一个模型存在，我们也看不见它。要看见物体，通常需要：

1. 光源发出光；
2. 光照到物体表面；
3. 物体表面反射一部分光；
4. 反射光进入相机；
5. 相机把结果显示在屏幕上。

因此，物体的颜色不是一个固定值，而是由多个因素共同决定：

```text
最终颜色 =
物体自身颜色
× 光照强度
× 表面反射特性
× 阴影关系
```

真实世界的光照非常复杂。实时游戏通常会使用近似算法，在“画面质量”和“每秒渲染几十帧”的性能要求之间做平衡。

#### 2. RGB 颜色

屏幕通常使用红、绿、蓝三种颜色混合显示画面：

```text
红色：R
绿色：G
蓝色：B
```

每个通道可用 `0 到 1` 表示：

```text
黑色 = (0, 0, 0)
白色 = (1, 1, 1)
红色 = (1, 0, 0)
绿色 = (0, 1, 0)
蓝色 = (0, 0, 1)
黄色 = (1, 1, 0)
```

注意：游戏中的颜色计算常常不应简单理解为“8 位整数颜色”。现代渲染中，许多计算会使用比屏幕显示范围更大的浮点数值，这与后面会学到的 HDR 有关。

### 三、法线：表面朝向决定光照

#### 1. 什么是法线

**法线（Normal）** 是一个垂直于物体表面的方向向量。

例如，一块水平地面向上，它的法线可写成：

```text
(0, 1, 0)
```

一个朝向右侧的平面，其法线大致是：

```text
(1, 0, 0)
```

法线不是位置，而是方向。它决定了表面“朝向哪里”。

#### 2. 为什么法线重要

同样一束光，照到不同朝向的表面，亮度不同。

想象太阳从上方照射：

- 地面朝上，能接收到较多光；
- 竖直墙面接收到较少光；
- 背向太阳的面接收不到直接光。

所以，渲染器必须知道每个像素对应表面的法线方向，才能计算受光强度。

### 四、最基础的漫反射光照

#### 1. 漫反射是什么

粗糙表面会把光向多个方向散射，例如：

- 墙面；
- 木头；
- 纸张；
- 石头；
- 未抛光的塑料。

这种表面光照效果叫作 **Diffuse Reflection（漫反射）**。

最常见的简化模型是 Lambert 漫反射模型：

```text
漫反射强度 = max(0, 法线方向 · 光线方向)
```

其中 `·` 是向量点积。

你不需要现在深入推导点积，只需理解：

- 两个方向越接近，点积越接近 `1`；
- 两个方向垂直，点积接近 `0`；
- 两个方向相反，点积为负数。

因此：

```text
表面正对光源 → 更亮
表面与光线垂直 → 较暗
表面背对光源 → 没有直接光
```

概念伪代码：

```glsl
float diffuse = max(dot(normal, lightDirection), 0.0);
vec3 color = albedo * lightColor * diffuse;
```

其中：

- `normal`：表面法线；
- `lightDirection`：从表面指向光源的方向；
- `albedo`：物体本身的基础颜色；
- `lightColor`：光源颜色；
- `diffuse`：当前表面获得的直接光强度。

### 五、高光反射：为什么金属会发亮

#### 1. 高光是什么

当你看见阳光在水面、金属、玻璃或汽车漆面上形成亮点时，这种亮点是 **Specular Reflection（镜面反射/高光）**。

高光与以下因素有关：

- 表面是否光滑；
- 光线方向；
- 相机观察方向；
- 表面法线方向。

例如：

- 粗糙水泥墙有弱而分散的高光；
- 镜面金属有强而集中的高光；
- 水面和玻璃有非常明显的反射。

#### 2. 观察方向为什么重要

漫反射主要取决于表面和光源之间的关系。

高光除了受光线和表面方向影响，还依赖相机位置。换一个角度看同一块金属，高亮区域会移动甚至消失。

所以，片元着色器除了需要：

```text
法线方向 N
光照方向 L
```

还需要：

```text
观察方向 V
```

这里的 `V` 是从表面指向相机的方向。

### 六、从传统光照到 PBR

传统游戏常使用 Phong 或 Blinn-Phong 等经验模型实现光照。这些方法容易理解、计算较快，但不同材质在不同环境下不一定真实。

现代游戏更常使用 **PBR（Physically Based Rendering，基于物理的渲染）**。

PBR 不等于“绝对真实”，而是使用更符合物理规律、更稳定的材质和光照模型。

它的价值在于：

- 同一种材质在不同光照环境下表现更合理；
- 美术人员更容易控制参数；
- 金属、塑料、木头、皮肤等材质区分更自然；
- 同一套资源可以更稳定地用于不同场景。

#### 1. PBR 中最重要的五张贴图

一个常见 PBR 材质至少可能包含：

| 贴图/参数 | 含义 | 例子 |
|---|---|---|
| Base Color / Albedo | 物体最基础的颜色 | 红色油漆、木纹颜色 |
| Normal | 模拟表面细节方向 | 砖块缝隙、皮革纹路 |
| Metallic | 表面是否具有金属属性 | 铁、铜、金、塑料 |
| Roughness | 表面粗糙程度 | 镜子低，水泥高 |
| Ambient Occlusion | 表现缝隙和遮挡区域的暗部 | 石块缝隙、墙角 |

### Base Color / Albedo

它表示物体在不考虑光照时最基本的反射颜色。

例如：

```text
红色塑料：偏红
木头：棕黄色纹理
铁：偏灰
草地：绿色纹理
```

对于非金属物体，可以近似理解为“物体本身的颜色”。

### Metallic

`Metallic` 通常是 0 到 1 的值：

```text
0：非金属
1：金属
```

例如：

```text
木头、石头、皮肤、塑料 → 通常接近 0
铁、铜、金、铝 → 通常接近 1
```

在大多数真实材质中，这个值通常不是连续随意调整的，而是接近 0 或接近 1。中间值通常用于混合材质、磨损区域等特殊情况。

金属与非金属的一个关键区别是：

- 非金属主要表现为自身颜色的漫反射；
- 金属的反射通常带有自身颜色，且漫反射很弱。

### Roughness

`Roughness` 表示表面粗糙程度：

```text
0：非常光滑
1：非常粗糙
```

粗糙度低：

- 高光集中；
- 反射更清晰；
- 类似镜面、抛光金属、水面。

粗糙度高：

- 高光范围更大、更模糊；
- 反射不明显；
- 类似水泥、布料、粗糙石头。

一个常见误解是：粗糙度不是“表面明暗程度”，而是“反射光分布得有多分散”。

### Normal Map

模型的三角形数量有限。如果只依赖几何形状表现细节，一个墙面上的每块砖、每道裂缝都需要额外三角形，成本很高。

法线贴图可以在不显著增加模型面数的情况下，改变像素级的表面朝向，使光照看起来像存在凹凸细节。

它的效果是：

```text
模型轮廓通常不变
但表面受光和阴影细节发生变化
```

例如，一面平整墙体加上砖块法线贴图后，看起来会有砖缝和凸起，但从侧面看，模型外轮廓仍然是平面。

### Ambient Occlusion，AO

AO 表示环境遮蔽，用于增强物体缝隙、接触面和角落的暗部。

例如：

- 两块石头接触的位置；
- 墙角；
- 角色衣服的褶皱；
- 桌腿与地面的接触位置。

AO 不是直接光照产生的硬阴影，它是对“环境光难以进入狭窄区域”的近似。

### 七、直接光和间接光

#### 1. 直接光 Direct Lighting

光线直接从光源照到物体表面，叫直接光。

例如：

- 手电筒照到墙面；
- 太阳照到地面；
- 路灯照到角色。

常见光源类型：

| 光源 | 特点 | 例子 |
|---|---|---|
| Directional Light | 所有光线方向相同，通常无距离衰减 | 太阳、月亮 |
| Point Light | 从一个点向四周发光 | 灯泡、火把 |
| Spot Light | 有方向和角度限制的锥形光 | 手电筒、舞台灯 |
| Area Light | 有面积的光源，阴影更柔和 | 窗户、灯箱 |

#### 2. 间接光 Indirect Lighting

光照到一个表面后会反射，再照亮其他表面，这种多次反射形成的光叫间接光。

例如：

- 阳光照到红墙，附近白墙会略带红色；
- 室内窗边的地面被阳光照亮后，也会微弱照亮旁边墙面；
- 房间角落不会绝对纯黑，因为仍有环境反射光。

真实间接光计算非常昂贵。实时游戏通常使用近似技术，例如：

- Ambient Light（环境光）；
- Light Probe（光照探针）；
- IBL（Image-Based Lighting，基于图像的光照）；
- 烘焙光照贴图；
- Screen Space GI；
- 实时光线追踪或路径追踪。

今天先理解：只有直接光会让画面看起来很“硬”和“假”，现代游戏需要一定形式的间接光或环境光。

### 八、IBL：让环境参与材质反射

**IBL（Image-Based Lighting）** 指使用环境图像为物体提供光照和反射信息。

例如，角色站在黄昏的沙漠中：

- 天空偏暖色；
- 地面反射偏黄；
- 金属盔甲会反射天空和周围环境；
- 阴影中的物体也不会完全黑。

游戏通常使用环境贴图，例如 Cubemap（立方体贴图）或 HDRI 环境图，近似模拟来自四周的环境光。

可以把它理解为：

```text
不是只看“场景中摆了哪些灯”
还要看“物体周围整体环境是什么颜色、什么亮度”
```

这对 PBR 很重要。没有合适环境光时，金属往往会显得像黑色或灰色塑料，因为金属最显著的视觉特征是反射环境。

### 九、阴影：如何知道某处被遮挡

#### 1. 阴影的本质

一个表面是否处于阴影中，取决于：

> 从该表面到光源之间，是否有其他物体挡住光线。

例如太阳照射地面时，如果角色站在光线方向上，角色后方的一部分地面收不到太阳直射，于是形成阴影。

#### 2. Shadow Map 的核心思路

实时游戏最常见的阴影技术是 **Shadow Map（阴影贴图）**。

它通常需要两步。

### 第一步：从光源视角渲染深度

把光源当成相机，从光源的视角观察场景。

这时不需要画颜色，只记录每个位置离光源最近的表面距离，也就是深度：

```text
光源看到的最近表面深度
→ 写入 Shadow Map
```

### 第二步：正常渲染画面时检查遮挡

从玩家相机正常渲染场景时，对每个像素：

1. 计算它在光源视角中的位置；
2. 查询 Shadow Map；
3. 比较当前像素到光源的距离，和 Shadow Map 中保存的最近深度；
4. 如果当前像素更远，说明中间有物体挡住光线，它处于阴影中。

概念流程：

```text
从光源看：地面前方有角色
    ↓
Shadow Map 记录角色表面深度
    ↓
从相机看：角色后方地面进行深度比较
    ↓
地面比 Shadow Map 记录的深度更远
    ↓
判定为阴影区域
```

#### 3. 阴影为什么容易出问题

Shadow Map 的分辨率有限，而且涉及不同坐标空间和深度比较，因此常有伪影。

| 问题 | 表现 | 常见原因 |
|---|---|---|
| Shadow Acne | 表面出现条纹、斑点或自阴影错误 | 深度精度和比较误差 |
| Peter Panning | 阴影与物体之间像悬空一样有缝隙 | 阴影偏移过大 |
| 锯齿 | 阴影边缘明显呈方块状 | 阴影贴图分辨率有限 |
| 闪烁 | 移动时阴影不稳定 | 精度、采样或级联切换问题 |

常见改进方法包括：

- Depth Bias：给深度比较增加小偏移；
- PCF：多次采样，使阴影边缘平滑；
- Cascaded Shadow Maps：为远近区域使用不同精度的阴影贴图，常用于太阳光。

### 十、HDR 与 Tone Mapping

#### 1. 为什么需要 HDR

现实中的亮度范围很大：

```text
夜晚角落：很暗
室内灯光：较亮
阳光反射：极亮
直接看太阳：极其亮
```

传统屏幕颜色范围有限，通常只能显示 `0 到 1`。但游戏在计算光照时，光照强度可能远大于 1：

```text
暗处：0.01
普通灯光：1.0
强反射：10.0
阳光直射：100.0
```

**HDR（High Dynamic Range，高动态范围）** 的含义是：在渲染过程中使用更宽的亮度范围保存颜色和光照数据。

它不是简单地“让画面更亮”，而是避免亮部和暗部信息过早丢失。

#### 2. Tone Mapping：映射回显示器可显示范围

显示器无法直接显示无限亮度，因此要把 HDR 颜色映射到普通屏幕范围，这一步叫 **Tone Mapping（色调映射）**。

目标是：

- 保留高亮区域的细节；
- 保留暗部层次；
- 不让整个画面发灰；
- 尽可能模拟人眼对亮度的感知。

例如强光下的天空不应该只是一块纯白色，仍应尽量保留云层、颜色和明暗变化。

#### 3. Bloom：为什么亮的物体会有光晕

**Bloom（泛光）** 模拟非常亮的物体在镜头或人眼中的扩散效果。

基本流程：

```text
原始 HDR 图像
    ↓
提取特别亮的区域
    ↓
对亮区进行模糊
    ↓
叠加回原图
```

Bloom 常用于：

- 太阳；
- 霓虹灯；
- 魔法特效；
- 明亮窗户；
- 夜晚灯光。

Bloom 太强会使画面模糊、发白，看起来像镜头失焦。因此它应当是辅助效果，不应替代正常光照。

### 十一、抗锯齿

#### 1. 什么是锯齿

屏幕由离散像素组成，斜线、远处细小物体和模型边缘容易出现阶梯状边缘，这叫 **Aliasing（锯齿）**。

例如：

```text
平滑斜线在低分辨率像素格上显示
→ 变成一格一格的阶梯
```

#### 2. 常见抗锯齿方案

| 技术 | 核心思路 | 特点 |
|---|---|---|
| MSAA | 在几何边缘使用更多采样 | 边缘效果较好，成本较高 |
| FXAA | 在屏幕后处理边缘 | 快，但可能让画面发糊 |
| TAA | 利用前后帧信息平滑 | 现代游戏常用，但可能有拖影 |
| DLSS/FSR/XeSS | 结合时间信息或算法重建画面 | 可提升性能和画质，但有工程复杂度 |

初学阶段先记住：

- MSAA 更偏向处理几何边缘；
- FXAA 是较便宜的后处理方法；
- TAA 常用于现代实时渲染，但依赖历史帧数据。

### 十二、渲染性能：为什么画面不能无限堆效果

实时渲染的约束是帧时间。

| 目标帧率 | 每帧预算 |
|---|---:|
| 30 FPS | 33.33 ms |
| 60 FPS | 16.67 ms |
| 120 FPS | 8.33 ms |

如果渲染一帧花费 25ms，那么理论帧率约为：

```text
1000 / 25 = 40 FPS
```

渲染性能常见瓶颈分两类。

#### 1. CPU 瓶颈

常见原因：

- Draw Call 太多；
- 场景对象过多；
- 可见性判断开销大；
- 每帧创建、销毁大量对象；
- 资源加载和逻辑更新阻塞主线程。

#### 2. GPU 瓶颈

常见原因：

- 分辨率太高；
- 三角形数量太多；
- Shader 太复杂；
- 阴影贴图太大；
- 后处理效果太多；
- 透明物体和屏幕覆盖面积过大；
- 纹理采样或显存带宽压力过高。

一个基础判断方法：

```text
降低分辨率后帧率明显提高
→ 更可能是 GPU 或像素填充相关问题

降低场景对象或 Draw Call 后帧率明显提高
→ 更可能是 CPU 提交相关问题
```

实际项目应使用性能分析工具验证，不能只靠猜测。

## 第 3 天：动画、物理与碰撞

**当天目标**：理解角色为什么能从“静止模型”变成自然运动的人物；理解物体如何受重力、速度和碰撞影响；理解动画系统与物理系统如何协作。

建议投入 6-8 小时。今天的核心不是复杂公式，而是建立这条链路：

```text
玩家输入
    ↓
游戏逻辑决定角色状态
    ↓
物理系统计算移动和碰撞
    ↓
动画系统生成角色姿态
    ↓
渲染系统显示最终角色
```

### 一、动画、物理和渲染分别负责什么

初学时很容易把“角色移动”和“角色动画”混在一起。它们实际是不同问题。

假设玩家按下 `W` 键让角色向前走。

| 系统 | 职责 | 结果 |
|---|---|---|
| 输入系统 | 读取玩家是否按下 `W` | 得到移动意图 |
| 游戏逻辑 | 判断角色是否能移动 | 切换角色状态 |
| 物理系统 | 检查角色是否撞墙、是否在地面上 | 更新角色实际位置 |
| 动画系统 | 让角色摆腿、摆手、转身 | 生成骨骼姿态 |
| 渲染系统 | 绘制角色模型 | 显示到屏幕 |

一个重要原则：

> 动画负责“看起来怎么动”，物理负责“实际上怎么移动和碰撞”。

例如角色播放跑步动画，不代表它真的已经向前移动；角色被墙挡住时，仍可以播放跑步动作，但位置不应该穿过墙。

### 二、骨骼动画：模型如何动起来

#### 1. 静态模型和骨骼模型

一个静态模型，例如石头、桌子、建筑，一般不需要局部变形。它整体移动、旋转、缩放即可。

```text
石头整体移动
→ 修改它的 Transform
```

角色、怪物、动物等模型不同。它们需要局部变形：

- 手臂摆动；
- 膝盖弯曲；
- 头部转动；
- 手指握住武器；
- 脸部做表情。

如果每一帧都直接修改模型的大量顶点，成本很高，也难以编辑。因此游戏通常使用 **骨骼动画（Skeletal Animation）**。

#### 2. 什么是骨骼

骨骼不是模型内部真实存在的骨头，而是一套用于控制模型变形的层级节点。

一个简化的人形骨骼可能是：

```text
Root
└── Hips
    ├── Spine
    │   └── Chest
    │       ├── Neck
    │       │   └── Head
    │       ├── LeftShoulder
    │       │   └── LeftArm
    │       │       └── LeftHand
    │       └── RightShoulder
    │           └── RightArm
    │               └── RightHand
    ├── LeftLeg
    │   └── LeftFoot
    └── RightLeg
        └── RightFoot
```

这里的父子关系非常重要。

如果身体向前移动，头、手、脚都会跟着移动；如果右手臂旋转，右手会跟着旋转，但头不会受影响。

这就是 **层级变换（Hierarchical Transform）**。

#### 3. 父节点如何影响子节点

假设角色手臂和手的关系如下：

```text
肩膀
└── 手臂
    └── 手
```

当肩膀旋转时：

- 手臂位置和朝向改变；
- 手的位置和朝向也改变。

当手臂旋转时：

- 手改变；
- 肩膀不变。

可以把它理解为现实中的人体关节：上臂带动前臂，前臂带动手掌。

数学上，子节点的世界变换通常可以概念化为：

```text
子节点世界矩阵 = 父节点世界矩阵 × 子节点局部矩阵
```

不需要手算矩阵，但要理解：

> 子节点的位置通常是相对于父节点定义的，而不是直接相对于整个世界定义的。

### 三、蒙皮：骨骼如何驱动模型顶点

仅有骨骼还不够。引擎还需要知道：

> 模型上的每个顶点，应该受哪些骨骼影响，以及每根骨骼影响多少。

这一步叫作 **Skinning（蒙皮）**。

例如角色手臂附近的一个顶点：

```text
上臂骨骼影响：0.7
前臂骨骼影响：0.3
```

这表示该顶点主要跟随上臂，也部分跟随前臂。

一个顶点通常只保留有限数量的骨骼影响，例如 4 根骨骼：

```text
boneIndices = [3, 4, 7, 0]
boneWeights = [0.55, 0.30, 0.15, 0.0]
```

对应含义：

```text
第 3 根骨骼影响 55%
第 4 根骨骼影响 30%
第 7 根骨骼影响 15%
```

最终顶点位置会根据多根骨骼的变换结果做加权混合。

概念公式：

```text
最终顶点位置 =
骨骼A变换后的顶点 × 权重A
+ 骨骼B变换后的顶点 × 权重B
+ ...
```

这就是为什么手肘弯曲时，手臂网格能够平滑变形，而不是像几块硬塑料一样断开。

#### 1. CPU 蒙皮和 GPU 蒙皮

骨骼动画可在 CPU 或 GPU 上计算。

| 方式 | 特点 |
|---|---|
| CPU 蒙皮 | CPU 直接计算变形后的顶点，简单但大量角色时性能差 |
| GPU 蒙皮 | CPU 只上传骨骼矩阵，GPU 在顶点着色器中完成顶点变形，现代游戏更常见 |

GPU 蒙皮的基本过程：

```text
动画系统计算当前骨骼姿态
    ↓
得到每根骨骼的最终变换矩阵
    ↓
将骨骼矩阵上传给 GPU
    ↓
顶点着色器按骨骼权重变形顶点
    ↓
后续进入正常渲染流程
```

### 四、关键帧动画和插值

#### 1. 什么是关键帧

动画师不会为每一秒钟的每一帧都手动设置角色姿势。

例如 30 FPS 的一秒动画有 30 帧。如果一个 10 秒动作每帧都人工制作，工作量极大。

因此动画师会设置关键姿势，即 **Keyframe（关键帧）**：

```text
第 0 秒：角色站立
第 0.5 秒：角色抬起右脚
第 1 秒：角色右脚落地
```

引擎负责计算两个关键帧之间的中间状态，这个过程叫 **插值（Interpolation）**。

#### 2. 位置插值

最基础的位置插值叫线性插值，即 `Lerp`。

假设角色从位置 A 移动到位置 B：

```text
A = (0, 0, 0)
B = (10, 0, 0)
```

当进度为 `t` 时：

```text
t = 0   → 在 A
t = 0.5 → 在 A 和 B 的中间
t = 1   → 在 B
```

概念公式：

```text
result = A × (1 - t) + B × t
```

在代码中常写为：

```cpp
position = lerp(startPosition, endPosition, t);
```

其中 `t` 一般在 `0 到 1` 之间。

#### 3. 旋转插值

旋转不能简单像位置一样直接插值，否则可能发生角度跳变、旋转方向错误等问题。

游戏引擎通常使用 **四元数（Quaternion）** 表示旋转，并使用 `Slerp` 或类似方法平滑插值。

初学阶段只需记住：

- 欧拉角容易理解，例如 `(x, y, z)` 分别绕三个轴旋转；
- 欧拉角可能产生万向节死锁等问题；
- 四元数更适合稳定表示和插值旋转；
- 引擎内部常用四元数，编辑器界面可能仍显示欧拉角。

### 五、动画状态机

角色不能只播放一个动画。它常常需要在多个动作之间切换：

```text
Idle（待机）
Walk（走路）
Run（跑步）
Jump（跳跃）
Attack（攻击）
Hit（受击）
Death（死亡）
```

**动画状态机（Animation State Machine）** 用于管理这些状态，以及状态之间的切换条件。

例如：

```text
Idle
  ├── speed > 0.1 → Walk
  ├── isJumping → Jump
  └── attackPressed → Attack

Walk
  ├── speed <= 0.1 → Idle
  ├── speed > 4.0 → Run
  └── isJumping → Jump
```

用伪代码表示：

```cpp
if (isDead) {
    state = Death;
} else if (attackPressed) {
    state = Attack;
} else if (isJumping) {
    state = Jump;
} else if (speed > runThreshold) {
    state = Run;
} else if (speed > walkThreshold) {
    state = Walk;
} else {
    state = Idle;
}
```

实际项目中，状态优先级更复杂。例如死亡通常应覆盖攻击、走路等普通状态。

#### 1. 动画切换为什么需要混合

如果角色从待机动画立即跳到跑步动画，画面可能会突然抖动：

```text
上一帧：双手自然下垂
下一帧：双腿已跨开、手臂大幅摆动
```

为了避免突变，引擎会在一小段时间内将两个动画姿态混合，这叫作 **Animation Blend（动画混合）**。

例如：

```text
0.00 秒：100% Idle，0% Run
0.10 秒：70% Idle，30% Run
0.20 秒：40% Idle，60% Run
0.30 秒：0% Idle，100% Run
```

这样角色会自然地从站立过渡到跑步。

### 六、正向运动学和逆向运动学

#### 1. 正向运动学 FK

**Forward Kinematics，FK** 的含义是：

> 已知父骨骼的变换，逐级计算子骨骼的位置和姿态。

例如：

```text
旋转肩膀
→ 得到手臂位置
→ 得到手的位置
→ 得到手指位置
```

普通骨骼动画基本都依赖 FK。

#### 2. 逆向运动学 IK

**Inverse Kinematics，IK** 的含义是：

> 已知目标位置，反过来计算骨骼应该如何旋转。

例如角色要把手放到桌面上的某个位置：

```text
已知：手的目标位置
求解：肩膀、手臂、前臂应该旋转多少
```

IK 常见用途：

- 角色脚底贴合不平地面；
- 角色手准确抓住门把手或武器；
- 角色看向指定目标；
- 瞄准动作；
- 多足角色的落脚控制。

初学阶段只要理解：

```text
FK：从骨骼旋转推导末端位置
IK：从末端目标反推骨骼旋转
```

### 七、角色位置和动画位置

#### 1. In-Place Animation

**In-Place Animation** 指角色在动画中原地做跑步动作，模型本身没有向前移动。

角色实际向前移动由游戏逻辑或物理系统控制：

```text
动画：播放原地跑步
物理：每帧将角色位置向前推进
```

优点：

- 移动距离容易由程序精确控制；
- 网络同步和碰撞处理相对容易；
- 常用于普通角色控制。

#### 2. Root Motion

**Root Motion（根运动）** 指从动画的根骨骼位移中提取实际移动距离和旋转，用它来驱动角色位置。

例如一段翻滚动画中，角色根骨骼向前移动 2 米：

```text
动画根骨骼移动 2 米
→ 游戏对象真实移动 2 米
```

它适合：

- 近战攻击；
- 翻滚、冲刺；
- 处决动作；
- 高质量第三人称角色动作。

挑战在于：

- 仍需与碰撞系统协调；
- 角色不能因为动画位移直接穿过墙；
- 网络同步和状态修正会更复杂。

### 八、物理模拟基础

#### 1. 物理系统解决什么问题

物理系统用于模拟游戏世界中的运动和交互，例如：

- 重力；
- 物体下落；
- 子弹飞行；
- 推箱子；
- 车辆运动；
- 角色不能穿过墙；
- 物体碰撞后反弹或停下。

游戏物理通常不是完全精确的真实物理，而是为了稳定、可控和有趣而设计的近似模拟。

#### 2. 位置、速度、加速度

理解物理系统，先理解三个基本量：

| 名称 | 含义 | 单位示例 |
|---|---|---|
| 位置 Position | 物体在哪里 | 米 |
| 速度 Velocity | 物体移动多快、向哪里移动 | 米/秒 |
| 加速度 Acceleration | 速度变化多快 | 米/秒² |

例如一个物体自由下落：

```text
初始位置：10 米高
初始速度：0
重力加速度：向下
```

每一段时间内：

```text
速度逐渐变大
→ 下落越来越快
→ 位置不断下降
```

概念伪代码：

```cpp
velocity += acceleration * deltaTime;
position += velocity * deltaTime;
```

重力可写作：

```cpp
acceleration = (0, -9.8f, 0);
```

游戏中常根据手感调整重力值，不一定严格使用现实中的 `9.8`。

#### 3. 力和质量

牛顿第二定律：

```text
F = m × a
```

也可以写成：

```text
a = F / m
```

其中：

- `F`：力；
- `m`：质量；
- `a`：加速度。

例如施加相同大小的推力：

- 轻箱子加速度更大；
- 重箱子加速度更小。

概念代码：

```cpp
acceleration = force / mass;
velocity += acceleration * deltaTime;
position += velocity * deltaTime;
```

### 九、为什么物理通常使用固定时间步

游戏画面帧率不是固定的：

```text
某一帧：16ms
下一帧：20ms
再下一帧：35ms
```

如果物理计算完全跟着画面帧率走，碰撞和约束会变得不稳定。帧时间太长时，物体一次移动过远，可能直接穿过墙。

因此许多引擎让物理使用固定的更新间隔，例如：

```text
固定物理步长 = 1 / 60 秒
```

概念结构：

```cpp
accumulator += frameDeltaTime;

while (accumulator >= fixedDeltaTime) {
    physicsUpdate(fixedDeltaTime);
    accumulator -= fixedDeltaTime;
}

renderFrame();
```

这表示：

- 渲染可以随帧率变化；
- 物理按稳定的小步长运行；
- 某一帧耗时更长时，可能补跑多个物理步。

注意：固定时间步能提升稳定性，但不是万能的。极端掉帧时仍需限制补帧次数或采取降级策略，避免物理更新越来越落后。

### 十、碰撞检测

碰撞检测回答的问题是：

> 两个物体是否接触、重叠，或者即将相撞？

例如：

```text
角色和墙是否相撞？
子弹是否命中敌人？
角色是否站在地面？
车辆是否撞到护栏？
```

碰撞通常分为两个阶段。

#### 1. 粗检测 Broad Phase

粗检测的目标是快速排除绝大多数不可能发生碰撞的对象。

例如一张大地图中有：

```text
10,000 个物体
```

角色不需要和地图另一端的物体逐一检查碰撞。

粗检测会使用简单的空间划分或包围体，例如：

- 网格划分；
- 四叉树、八叉树；
- Sweep and Prune；
- AABB 包围盒；
- Bounding Sphere 包围球。

它的目标是找出“可能碰撞的对象对”。

```text
10,000 个物体
    ↓ 粗检测
只留下附近的 20 个候选物体
    ↓ 精检测
计算实际是否碰撞
```

#### 2. 精检测 Narrow Phase

精检测对候选对象进行更准确的几何判断。

常见碰撞形状：

| 形状 | 特点 | 适用对象 |
|---|---|---|
| Sphere | 计算快，但不够贴合 | 子弹、简单物体 |
| Box / AABB | 简单常用 | 箱子、墙体、触发区域 |
| Capsule | 适合站立角色 | 人形角色 |
| Convex Hull | 更贴合形状 | 道具、车辆部件 |
| Mesh Collider | 最精确但成本高 | 静态地形、复杂建筑 |

角色常使用 **Capsule Collider（胶囊碰撞体）**：

```text
顶部半球
中间圆柱
底部半球
```

原因是它比盒子更适合人物移动：

- 不容易卡在墙角；
- 上下圆弧更容易滑过小障碍；
- 计算成本比复杂网格低。

### 十一、碰撞响应

检测到碰撞后，系统还需要回答：

> 碰撞发生后应该怎么办？

这叫作 **碰撞响应（Collision Response）**。

不同对象的响应完全不同。

| 场景 | 可能的响应 |
|---|---|
| 角色撞墙 | 阻止角色继续进入墙体 |
| 子弹击中敌人 | 造成伤害、生成特效、销毁子弹 |
| 角色进入触发区 | 开始任务、播放过场动画 |
| 箱子落地 | 停止下落、可能弹起 |
| 汽车撞护栏 | 改变速度和方向，播放碰撞音效 |

因此要区分：

```text
Collider：定义碰撞形状
Collision Detection：判断是否发生接触
Collision Response：处理碰撞结果
Trigger：只检测进入/离开，不产生物理阻挡
```

一个触发器的例子：

```text
玩家进入传送门范围
→ 触发进入事件
→ 切换场景

玩家可以穿过传送门区域
→ 不需要物理阻挡
```

### 十二、刚体与约束

#### 1. 刚体 Rigidbody

**刚体** 是指在模拟中不会被拉伸或压缩的物体。大多数游戏物理对象都可近似看作刚体。

刚体常见属性：

```text
质量 Mass
位置 Position
旋转 Rotation
线速度 Linear Velocity
角速度 Angular Velocity
碰撞体 Collider
摩擦 Friction
弹性 Restitution
```

例如箱子从空中落下：

```text
重力使箱子向下加速
    ↓
箱子与地面碰撞
    ↓
碰撞响应修正位置和速度
    ↓
根据弹性决定是否反弹
    ↓
根据摩擦决定是否滑动
```

#### 2. 静态刚体、动态刚体和运动学刚体

| 类型 | 含义 | 示例 |
|---|---|---|
| Static | 不移动，作为环境碰撞物 | 地面、墙壁、建筑 |
| Dynamic | 受力、重力和碰撞影响 | 箱子、球、碎片 |
| Kinematic | 由程序直接控制移动，但可参与碰撞 | 电梯、移动平台、门 |

通常不应把整个复杂场景都设置成动态刚体，因为物理计算成本会迅速增加。

#### 3. 约束 Constraint

约束表示物体之间的运动限制。

例如：

- 门只能绕铰链旋转；
- 秋千只能在绳索允许的范围摆动；
- 两个物体通过弹簧连接；
- 车辆轮胎和车身通过悬挂系统连接。

常见约束类型：

```text
Fixed Joint：完全固定
Hinge Joint：绕一个轴旋转
Spring Joint：弹簧连接
Slider Joint：沿一个方向滑动
```

### 十三、角色控制器

很多游戏角色不会完全使用动态刚体控制。

原因是纯物理角色常出现：

- 走路时不稳定；
- 在斜坡和台阶上卡住；
- 被轻微碰撞后摔倒；
- 网络同步困难；
- 操作反馈不够直接。

因此大量游戏使用 **Character Controller（角色控制器）**：

```text
玩家输入目标移动方向
    ↓
角色控制器计算预期移动距离
    ↓
使用胶囊体进行扫掠检测
    ↓
遇墙停止或沿墙滑动
    ↓
检测地面、坡度、台阶
    ↓
更新角色最终位置
```

这种设计偏向“可控的游戏体验”，而不是追求角色像普通箱子一样受物理完全驱动。

### 十四、动画与物理如何协作

一个较常见的角色更新流程如下：

```text
1. 读取输入
2. 得到期望移动方向和速度
3. 角色控制器检测地面、墙壁、坡度
4. 计算角色实际位置和速度
5. 将实际速度传给动画状态机
6. 状态机选择 Idle、Walk、Run、Jump 等动画
7. 混合动画，生成最终骨骼姿态
8. GPU 蒙皮变形角色顶点
9. 渲染角色
```

注意其中的关键数据流：

```text
物理实际速度
    ↓
动画参数 speed
    ↓
选择走路或跑步动画
```

不要只根据玩家输入播放跑步动画。因为角色可能被墙挡住，实际速度为零，此时更合理的表现可能是停止，或播放“推动墙体”的特殊动作。

### 十五、今天的完整知识图

```text
动画资源
    ↓
关键帧和插值
    ↓
动画状态机选择当前动作
    ↓
动画混合生成当前骨骼姿态
    ↓
骨骼矩阵上传 GPU
    ↓
GPU 蒙皮变形角色网格
    ↓
渲染角色

同时：

输入
    ↓
游戏逻辑
    ↓
角色控制器 / 物理系统
    ↓
碰撞检测
    ↓
碰撞响应
    ↓
最终位置、速度和落地状态
    ↓
反馈给动画状态机
```

### 练习 3：写出最小角色更新伪代码

```cpp
void updateCharacter(float deltaTime) {
    Vector2 input = readMoveInput();

    Vector3 desiredDirection = convertInputToWorldDirection(input);
    Vector3 desiredVelocity = desiredDirection * moveSpeed;

    CharacterMoveResult result =
        characterController.move(desiredVelocity * deltaTime);

    animator.setFloat("speed", result.actualHorizontalSpeed);
    animator.setBool("isGrounded", result.isGrounded);
    animator.setFloat("verticalVelocity", result.verticalVelocity);

    if (attackPressed()) {
        animator.trigger("attack");
    }
}
```

不需要运行这段代码。重点是理解：

- 输入只表达玩家意图；
- `CharacterController` 计算能否真正移动；
- 动画参数应尽量来自实际移动结果；
- 动画与物理系统通过状态、速度和事件通信。

## 第 4 天：场景、实体组件、资源与引擎工程化

**当天目标**：理解游戏引擎如何管理一个复杂世界，如何加载模型、贴图、音频等文件，以及底层引擎如何向游戏玩法和编辑器提供能力。

今天要解决的不是“如何画一个角色”，而是：

> 场景中有几千个物体时，引擎如何知道它们是什么、在哪里、要更新什么、该加载哪些文件，并把它们交给渲染、动画、物理和游戏逻辑系统？

建议投入 6-8 小时。

### 一、一个游戏场景到底是什么

可以把 **场景（Scene）** 理解为某个游戏时刻的世界状态。

例如一个关卡场景可能包括：

```text
地形
建筑物
角色
敌人
树木和石头
相机
太阳光
背景音乐
NPC
触发器
UI
```

每一个场景对象都需要保存一些信息：

```text
它是什么？
它在哪里？
它有什么能力？
它引用了哪些模型、贴图、音频？
它是否要参与渲染、物理、动画或逻辑更新？
```

如果没有统一管理方式，游戏对象一多，代码会迅速混乱。

### 二、游戏对象：Entity、GameObject 和 Component

不同引擎的名称不同，但核心思想类似。

| 名称 | 常见含义 |
|---|---|
| GameObject | Unity 常用名称，表示场景中的一个对象 |
| Entity | ECS 架构常用名称，通常只是一个身份 ID |
| Actor | Unreal 常用名称，表示可放入场景的对象 |
| Component | 附加到对象上的一种能力或数据 |

初学时可以把一个对象理解为：

```text
对象 = 身份 + 组件
```

例如一盏路灯：

```text
StreetLamp
├── Transform Component
├── Mesh Renderer Component
├── Light Component
└── Audio Component（可选）
```

一个角色：

```text
Player
├── Transform Component
├── Mesh Renderer Component
├── Animator Component
├── Capsule Collider Component
├── Character Controller Component
├── Audio Component
├── Health Component
└── Player Controller Script
```

这里的关键设计理念是：

> 不要为每一种游戏对象都写一个巨大的专属类，而是用小而独立的组件组合出对象能力。

### 三、为什么不直接写一个“大而全”的角色类

刚开始学习时，很容易写出类似这样的代码：

```cpp
class Player {
public:
    Vector3 position;
    Vector3 velocity;

    Mesh mesh;
    Texture texture;
    AudioClip footstepSound;

    void move();
    void render();
    void playAnimation();
    void detectCollision();
    void updateAI();
    void saveData();
};
```

小项目中这能运行，但大型项目会出现问题：

- `Player` 同时负责移动、渲染、动画、碰撞、音频和存档；
- `Enemy`、`NPC`、`Vehicle` 等类会复制大量类似逻辑；
- 只会发光的物体也被迫带上无关功能；
- 修改一个功能可能影响整个大类；
- 很难批量处理同一类功能，例如“更新所有动画”。

更合理的思路是拆分职责：

```text
Player Entity
├── Transform
├── RenderMesh
├── Animator
├── CharacterController
├── Health
├── PlayerInput
└── PlayerScript
```

这样引擎可以：

```text
渲染系统：处理所有带 RenderMesh 的实体
动画系统：处理所有带 Animator 的实体
物理系统：处理所有带 Collider 的实体
音频系统：处理所有带 AudioSource 的实体
```

### 四、ECS：实体、组件、系统

**ECS（Entity Component System）** 是现代游戏引擎常见的架构思想。

它由三部分组成。

#### 1. Entity：实体

实体通常只是一个唯一 ID：

```text
Entity 1001：玩家
Entity 1002：敌人
Entity 1003：太阳
Entity 1004：木箱
```

实体本身不一定包含实际功能。它的意义是把多个组件关联起来。

可以把它理解为身份证号码：

```text
实体 ID = “这是同一个对象”的标识
```

#### 2. Component：组件

组件通常只保存某一类数据。

例如：

```cpp
struct Transform {
    Vector3 position;
    Quaternion rotation;
    Vector3 scale;
};

struct Velocity {
    Vector3 value;
};

struct Health {
    float current;
    float maximum;
};
```

组件的特点是：

- 数据职责单一；
- 容易组合；
- 不应把大量无关逻辑混在一起；
- 同类型数据通常可以集中存储和批量处理。

#### 3. System：系统

系统负责处理特定类型的组件。

例如移动系统：

```cpp
for each entity with Transform and Velocity:
    transform.position += velocity.value * deltaTime;
```

渲染系统：

```cpp
for each entity with Transform and MeshRenderer:
    submitDrawCommand(entity);
```

生命系统：

```cpp
for each entity with Health:
    if health.current <= 0:
        markEntityAsDead(entity);
```

ECS 的基本结构可以写成：

```text
Entity：对象身份
Component：对象数据
System：处理符合条件组件的逻辑
```

### 五、ECS 的优点和代价

#### 1. ECS 的优点

### 组合灵活

一个“带火焰效果的箱子”不需要新建复杂类别：

```text
Box Entity
├── Transform
├── MeshRenderer
├── Collider
├── Rigidbody
└── FireEffect
```

### 批量处理更自然

渲染系统不需要知道“这是玩家还是敌人”，它只关心：

```text
它是否有 Transform 和 MeshRenderer？
```

### 更适合性能优化

同种组件可连续存储。例如所有 `Transform` 放在连续内存中，CPU 批量遍历时缓存效率更高。

### 降低继承层级复杂度

传统继承可能变成：

```text
GameObject
└── Character
    └── CombatCharacter
        ├── PlayerCharacter
        └── EnemyCharacter
```

随着功能增加，继承关系很容易失控。ECS 更偏向组合：

```text
Player = Transform + Animator + Health + Input
Enemy = Transform + Animator + Health + AI
```

#### 2. ECS 的代价

ECS 不是所有项目的唯一答案。

常见代价：

- 对初学者不如面向对象直观；
- 调试时对象逻辑分散在多个系统；
- 系统执行顺序需要清楚设计；
- 组件之间的依赖关系需要管理；
- 复杂、独特的对象行为可能需要额外组织方式。

实际引擎常采用混合方案：

```text
核心高频数据：ECS 或数据导向设计
复杂玩法对象：脚本、面向对象或行为树
编辑器对象组织：场景图和组件模型
```

### 六、场景图：对象的层级关系

**场景图（Scene Graph）** 是按父子关系组织场景对象的结构。

例如：

```text
World
├── MainCamera
├── SunLight
├── Environment
│   ├── Terrain
│   ├── House_A
│   └── Trees
└── Player
    ├── Weapon
    └── CameraAnchor
        └── PlayerCamera
```

场景图特别适合表达空间从属关系。

例如武器挂在角色手上：

```text
Player
└── RightHand
    └── Sword
```

当角色移动或手臂摆动时，剑会自然跟随，因为剑的局部变换是相对于手定义的。

### 场景图和 ECS 的区别

两者不冲突，职责不同：

| 概念 | 主要解决的问题 |
|---|---|
| 场景图 | 谁是谁的父节点，空间变换如何传递 |
| ECS | 对象拥有哪些数据，哪些系统要批量处理它们 |

一个对象可以同时处于场景图中，也作为 ECS 实体存在。

例如：

```text
玩家实体
├── 在 ECS 中：Transform、Animator、Collider、Health
└── 在场景图中：属于 LevelRoot，武器是其子节点
```

### 七、Prefab：可复用对象模板

**Prefab（预制体）** 是保存好的对象模板。

例如，一个敌人不仅仅是模型，还包含：

```text
模型
材质
骨骼动画
碰撞体
生命值
AI 脚本
音效配置
掉落物配置
```

如果每生成一个敌人都手动添加这些组件，工作量大且容易出错。

于是将它保存为：

```text
Goblin.prefab
```

生成敌人时：

```text
加载 Prefab
    ↓
创建实体
    ↓
复制或实例化组件配置
    ↓
放入场景指定位置
```

Prefab 常用于：

- 玩家角色；
- 敌人；
- 武器；
- 特效；
- UI 控件；
- 可破坏物体；
- 建筑模块。

注意：Prefab 是数据模板，不等于运行时实体本身。

```text
Enemy.prefab：敌人模板
Enemy #1：场景中的具体敌人
Enemy #2：场景中的另一个具体敌人
```

### 八、资源系统：引擎如何管理文件

#### 1. 什么是资源

游戏资源（Asset）包括：

```text
模型：Mesh
贴图：Texture
材质：Material
Shader
动画：Animation Clip
音频：Audio Clip
场景：Scene
预制体：Prefab
字体：Font
脚本：Script
配置数据：JSON、二进制表、数据表
```

这些资源通常来自美术、关卡、动画、音频和程序等不同岗位。

资源系统需要解决：

- 文件在哪里；
- 如何导入；
- 如何解析；
- 如何缓存；
- 如何引用；
- 不再使用时何时释放；
- 如何处理资源之间的依赖关系。

#### 2. 源资源和运行时资源

美术制作的软件和游戏运行时使用的文件不一定相同。

例如：

```text
Blender 的 .blend
Maya 的 .mb / .ma
Photoshop 的 .psd
```

这些通常是制作源文件，不适合直接在游戏中加载。

游戏引擎会经过导入和转换：

```text
源文件
    ↓ 导入器 Importer
引擎内部资源格式
    ↓ 烘焙/压缩 Cook
适合目标平台的运行时文件
    ↓
游戏加载使用
```

例如：

```text
角色模型 .fbx
    ↓
提取网格、骨骼、动画、材质引用
    ↓
转换为引擎运行时格式
    ↓
压缩纹理、生成 Mipmap、优化顶点数据
    ↓
打包进游戏资源包
```

这条过程通常称为 **Asset Pipeline（资源管线）**。

### 九、资源引用：为什么不应到处写文件路径

初学项目常见写法：

```cpp
loadTexture("assets/textures/wood.png");
```

这在小项目能用，但在大型游戏中有问题：

- 文件移动或改名后，所有硬编码路径都可能失效；
- 很难知道某个资源被谁使用；
- 无法方便地做资源打包、热更新和跨平台转换；
- 重复加载同一资源会浪费内存；
- 难以控制资源生命周期。

引擎通常使用 **资源 ID、GUID 或资源句柄（Handle）**。

概念示例：

```text
TextureHandle 301
MaterialHandle 85
MeshHandle 907
```

对象不直接关心文件路径，只保存资源引用：

```cpp
struct MeshRenderer {
    MeshHandle mesh;
    MaterialHandle material;
};
```

资源系统内部再负责：

```text
Handle 907
    ↓
找到对应资源记录
    ↓
判断是否已加载
    ↓
必要时从磁盘或资源包读取
    ↓
创建 GPU 资源
    ↓
返回可用网格数据
```

### 十、资源缓存与引用计数

假设场景中有 100 棵相同的树。

错误做法：

```text
每棵树都单独加载一次 Tree.mesh 和 Tree.png
```

这会重复占用内存和加载时间。

正确思路：

```text
Tree.mesh 只加载一份
Tree.png 只加载一份
100 个树实体共享这些资源
```

资源缓存的基本概念：

```text
请求资源
    ↓
缓存中是否已存在？
    ├── 是：直接返回现有资源
    └── 否：加载资源，放入缓存，再返回
```

当没有对象再使用某个资源时，引擎可以选择：

- 立即释放；
- 在内存紧张时释放；
- 保留一段时间，防止频繁加载；
- 对常驻资源始终保留。

**引用计数（Reference Count）** 是一种常见方案：

```text
资源被 3 个对象使用 → 引用计数 = 3
一个对象销毁 → 引用计数 = 2
全部对象销毁 → 引用计数 = 0
```

计数为零后，资源可以成为释放候选。

实际引擎还常用弱引用、异步加载、LRU 缓存、资源分组等机制处理复杂情况。

### 十一、同步加载与异步加载

#### 1. 同步加载

同步加载表示：程序必须等资源加载完才能继续。

```cpp
Texture texture = loadTextureSync("large_map_texture");
```

问题是大型资源可能需要较长时间：

```text
开始加载大贴图
    ↓
主线程等待
    ↓
游戏画面卡住
    ↓
资源加载完成后才恢复
```

同步加载适合：

- 游戏启动阶段；
- 加载界面；
- 很小且必须立刻可用的资源；
- 调试工具。

#### 2. 异步加载

异步加载表示：启动加载任务后，主线程可以继续运行。

```text
请求加载角色模型
    ↓
后台线程读取和解压文件
    ↓
主线程继续显示场景或加载界面
    ↓
资源准备完成
    ↓
主线程/GPU 创建最终资源
    ↓
角色可显示
```

异步加载适合：

- 开放世界；
- 场景流式加载；
- 大型贴图、模型、音频；
- 角色和特效按需加载。

需要注意：GPU 资源创建、场景对象修改等操作可能要求在特定线程执行。异步加载不是“任何代码都放后台线程”，而是要明确线程边界。

### 十二、序列化：如何保存和恢复场景

**序列化（Serialization）** 是把内存中的对象状态转换为可保存或传输的数据。

例如一个场景中的灯：

```text
Light Entity
├── position = (3, 5, -2)
├── color = (1.0, 0.8, 0.6)
├── intensity = 4.0
└── range = 10.0
```

可以保存成类似 JSON 的文本：

```json
{
  "name": "WarmLamp",
  "transform": {
    "position": [3, 5, -2],
    "rotation": [0, 0, 0, 1],
    "scale": [1, 1, 1]
  },
  "light": {
    "color": [1.0, 0.8, 0.6],
    "intensity": 4.0,
    "range": 10.0
  }
}
```

下次打开场景时：

```text
读取文件
    ↓
创建实体
    ↓
恢复 Transform、Light 等组件数据
    ↓
场景恢复
```

序列化用于：

- 保存场景；
- 保存 Prefab；
- 保存玩家存档；
- 网络同步；
- 编辑器撤销/重做；
- 热更新数据。

### 十三、脚本系统：游戏玩法如何使用引擎能力

引擎底层通常由 C++、Rust 或其他高性能语言实现；具体玩法逻辑常由脚本层编写，例如 C#、Lua、Python 风格 DSL，或引擎自己的可视化脚本。

例如“玩家捡起金币”并不需要写进底层渲染器或物理引擎：

```text
玩家进入金币触发器
    ↓
触发游戏脚本
    ↓
金币数量 +1
    ↓
播放拾取音效
    ↓
生成粒子特效
    ↓
销毁金币实体
    ↓
更新 UI
```

脚本系统需要能够调用引擎提供的 API：

```cpp
entity.getTransform().setPosition(newPosition);
audio.play("coin_pickup");
ui.setText("coinCount", count);
scene.destroyEntity(coinEntity);
```

引擎还需要把对象和组件暴露给编辑器和脚本层。这涉及 **反射（Reflection）** 或 **元数据（Metadata）**。

### 十四、反射和元数据

反射的简单理解是：

> 程序不仅能使用对象的数据，还能在运行时知道“这个对象有哪些字段、字段类型是什么、能否在编辑器中显示和修改”。

例如一个脚本组件：

```cpp
class RotatingObject {
public:
    float speed = 90.0f;
    bool clockwise = true;
};
```

如果引擎没有元数据，编辑器无法自动知道：

```text
speed 应显示为数值输入框
clockwise 应显示为复选框
```

有了元数据后，编辑器可以自动生成属性面板：

```text
RotatingObject
├── Speed: [ 90.0 ]
└── Clockwise: [x]
```

元数据还可以包含：

- 字段名称；
- 类型；
- 默认值；
- 合法范围；
- 是否只读；
- 是否需要保存；
- 是否能在网络中同步；
- 是否能被脚本访问。

反射和元数据是“引擎功能能被工具和内容生产流程使用”的重要基础。

### 十五、编辑器与运行时

#### 1. 运行时 Runtime

运行时是玩家真正运行游戏的环境，重点是：

- 性能；
- 稳定性；
- 资源占用；
- 平台兼容；
- 游戏功能。

#### 2. 编辑器 Editor

编辑器是开发者创建游戏内容的工具，重点是：

- 放置对象；
- 调整组件参数；
- 编辑场景；
- 导入资源；
- 编辑材质；
- 调试脚本；
- 查看性能和日志。

一个简单编辑器界面通常包括：

```text
Hierarchy：场景对象树
Inspector：当前对象的组件和属性
Viewport：场景预览窗口
Project/Assets：资源浏览器
Console：日志和报错
Profiler：性能分析
```

编辑器和运行时常共享底层引擎模块，但编辑器会额外拥有选择、拖拽、撤销重做、属性编辑、资源导入等功能。

### 十六、日志、断言和性能分析

大型引擎不能只在“程序崩溃后”才发现问题。

#### 1. 日志 Logging

日志用于记录运行过程：

```cpp
LOG_INFO("Loaded scene: Forest");
LOG_WARNING("Texture missing mipmaps: wall.png");
LOG_ERROR("Failed to load mesh: player.mesh");
```

日志级别常见为：

```text
Debug：调试细节
Info：正常运行信息
Warning：潜在问题，但程序可继续
Error：明确错误
Fatal：无法继续运行
```

#### 2. 断言 Assert

断言用于检查“理论上必须成立”的条件：

```cpp
assert(material != nullptr);
```

如果材质为空，说明程序状态不符合预期。开发阶段应尽早暴露问题，而不是继续运行到更难排查的位置。

#### 3. Profiler 性能分析器

性能分析器用于回答：

```text
到底是哪里慢？
```

它可以帮助查看：

- 主线程耗时；
- 渲染线程耗时；
- GPU 耗时；
- Draw Call 数量；
- 三角形数量；
- 内存和显存占用；
- 资源加载耗时；
- 某个函数调用次数。

性能优化必须基于测量。例如画面卡顿时，不能先假设“肯定是 Shader 太复杂”，也可能是 AI、资源加载或大量对象创建造成主线程阻塞。

### 十七、多线程：为什么引擎需要同时做多件事

现代 CPU 有多个核心。游戏引擎为了避免一个线程承担所有工作，通常会拆分任务。

典型线程可能包括：

```text
主线程：输入、游戏逻辑、场景更新
渲染线程：准备和提交渲染命令
资源加载线程：读取、解压和解析资源
音频线程：音频混音与播放
网络线程：收发网络消息
工作线程池：执行可并行任务
```

一个简化例子：

```text
主线程更新角色位置
    ↓
生成本帧渲染命令
    ↓
渲染线程提交给 GPU

同时：

资源线程加载远处区域的贴图和模型
    ↓
加载完成后通知主线程
    ↓
主线程安全地把资源加入场景
```

### 多线程的难点

多线程不是免费性能。

如果两个线程同时修改同一份数据，会出现竞争问题：

```text
主线程正在删除一个实体
资源线程尝试给该实体添加模型
```

可能导致崩溃或错误数据。

常见解决思路：

- 锁（Mutex）保护共享数据；
- 消息队列；
- 命令缓冲区；
- 不可变数据；
- 双缓冲；
- 将对象修改集中到主线程；
- 使用任务系统管理依赖。

初学阶段最重要的原则：

> 先明确数据由谁拥有、哪个线程可以修改它，再考虑并行执行。

### 十八、今天的完整流程：加载并显示一个角色

下面把第四天内容串起来。

```text
关卡文件 / 场景文件
    ↓
反序列化场景数据
    ↓
创建 Player Entity
    ↓
添加 Transform、Animator、Collider、CharacterController 等组件
    ↓
MeshRenderer 持有 Mesh 和 Material 的资源句柄
    ↓
资源系统检查模型、贴图、动画是否已加载
    ↓

```

### 练习 3：写一个最小 ECS 伪代码

```cpp
using Entity = uint32_t;

struct Transform {
    Vector3 position;
};

struct Velocity {
    Vector3 value;
};

void updateMovement(float deltaTime) {
    for (Entity entity : entitiesWith<Transform, Velocity>()) {
        Transform& transform = getComponent<Transform>(entity);
        Velocity& velocity = getComponent<Velocity>(entity);

        transform.position += velocity.value * deltaTime;
    }
}
```

理解这段代码：

- 该系统不关心实体是玩家、敌人还是子弹；
- 只要它同时具有 `Transform` 和 `Velocity`，就会被移动系统更新；
- 增加一个新对象类型时，不需要修改 `updateMovement`。

### 二、从游戏启动开始理解引擎

一个游戏程序通常从 `main` 函数或平台入口开始。

概念伪代码：

```cpp
int main() {
    Engine engine;

    engine.initialize();
    engine.loadInitialScene("MainMenu.scene");

    while (engine.isRunning()) {
        engine.tick();
    }

    engine.shutdown();
    return 0;
}
```

这段代码可以拆为三个阶段。

#### 1. 初始化阶段

```cpp
engine.initialize();
```

可能完成：

```text
创建游戏窗口
初始化图形 API
初始化 GPU 渲染设备
初始化输入系统
初始化音频设备
初始化物理系统
初始化资源系统
初始化脚本运行环境
创建线程池
读取游戏配置
```

例如渲染系统初始化后，才能创建纹理、Shader、深度缓冲区等 GPU 资源。

#### 2. 加载初始场景

```cpp
engine.loadInitialScene("MainMenu.scene");
```

可能完成：

```text
读取场景文件
反序列化场景数据
创建场景实体
加载模型、贴图、音频、动画等依赖资源
创建相机和光源
激活初始脚本
```

如果资源很多，引擎通常会展示加载界面，并用异步任务逐步加载。

#### 3. 主循环阶段

```cpp
while (engine.isRunning()) {
    engine.tick();
}
```

这是游戏持续运行的核心。每次 `tick()` 代表推进一帧。

### 三、一帧中通常发生什么

一个简化的帧更新过程如下：

```cpp
void Engine::tick() {
    float deltaTime = timer.getDeltaTime();

    inputSystem.update();
    networkSystem.update();
    scriptSystem.update(deltaTime);
    physicsSystem.updateFixedStep(deltaTime);
    animationSystem.update(deltaTime);
    sceneSystem.updateTransforms();

    renderSystem.render(scene);
    audioSystem.update(listener);

    windowSystem.present();
}
```

不同引擎的具体顺序会不同，但基本原则一致：

- 先获取外部输入；
- 再更新游戏状态；
- 再更新物理和动画；
- 最后根据最新状态渲染画面。

### 四、完整案例：玩家按下 W 键

下面用一个第三人称角色移动作为综合案例。

### 阶段 1：输入系统读取按键

玩家按下键盘 `W`。

操作系统会将键盘事件传递给游戏窗口，输入系统记录当前状态：

```cpp
bool moveForward = input.isKeyPressed(KeyCode::W);
```

输入系统通常不直接移动角色。它只提供输入数据，例如：

```text
W 是否按下
鼠标移动了多少
手柄摇杆方向
鼠标左键是否点击
```

可以将二维移动输入表达为：

```text
horizontal = 0
vertical = 1
```

也就是“向前移动”的意图。

### 阶段 2：游戏逻辑转换输入意图

游戏逻辑读取输入，决定玩家希望往哪个方向移动。

```cpp
Vector2 moveInput = input.getMoveAxis();
```

但 `(0, 1)` 只是输入坐标，并不一定是世界中的真实方向。

第三人称游戏通常要参考相机朝向：

```text
相机向前方向：cameraForward
相机向右方向：cameraRight
输入：moveInput
```

得到世界空间的移动方向：

```cpp
Vector3 moveDirection =
    cameraForward * moveInput.y +
    cameraRight * moveInput.x;
```

然后根据角色速度计算期望速度：

```cpp
Vector3 desiredVelocity = moveDirection * moveSpeed;
```

此时仍只是“期望移动”，还没有真正修改角色位置。

### 阶段 3：角色控制器和物理系统处理移动

角色控制器接收期望位移：

```cpp
Vector3 desiredDisplacement = desiredVelocity * deltaTime;
characterController.move(desiredDisplacement);
```

角色控制器通常会执行：

```text
检查是否在地面
检查前方是否有墙
检查是否能够走上台阶
检查坡度是否过陡
检查是否撞到其他碰撞体
计算碰撞后的实际位移
```

可能出现三种结果。

### 情况 1：前方没有障碍

```text
期望向前移动 0.1 米
实际移动 0.1 米
```

角色位置更新。

### 情况 2：前方有墙

```text
期望向前移动 0.1 米
实际移动 0 米
```

角色不应穿过墙。

### 情况 3：斜向撞到墙

```text
期望向右前方移动
墙阻挡了向右方向
仍允许沿墙向前滑动
```

这就是常见的“沿墙滑动”行为。

角色控制器通常还会输出状态：

```cpp
MoveResult result;
result.actualVelocity;
result.isGrounded;
result.hitWall;
result.hitCeiling;
```

这些结果会传给后续动画和游戏逻辑。

### 阶段 4：动画状态机决定播放什么动作

动画系统不会只依赖 `W` 键是否按下，而是应结合真实移动结果。

例如：

```cpp
animator.setFloat("speed", result.actualVelocity.length());
animator.setBool("isGrounded", result.isGrounded);
animator.setBool("hitWall", result.hitWall);
```

动画状态机可能依据参数做判断：

```text
speed = 0，且在地面上
    → Idle

0 < speed < 跑步阈值，且在地面上
    → Walk

speed >= 跑步阈值，且在地面上
    → Run

不在地面上，向上速度大于 0
    → Jump

不在地面上，向下速度小于 0
    → Fall
```

如果角色想移动但被墙挡住：

```text
输入：W 按下
实际速度：0
```

此时不应继续播放普通跑步动画。具体行为由游戏设计决定：

```text
播放 Idle
或播放 PushWall
或保持 Run 但不位移
```

关键是：动画状态机需要使用合理的游戏状态，而不应完全脱离物理结果。

### 阶段 5：动画系统生成骨骼姿态

假设动画状态机选择了 `Run` 动画。

动画系统会：

```text
读取 Run 动画当前时间点的关键帧
    ↓
插值得到每根骨骼当前的局部变换
    ↓
根据父子层级计算骨骼世界变换
    ↓
生成骨骼矩阵数组
    ↓
和其他动画状态进行混合
```

例如：

```text
Idle 权重：20%
Run 权重：80%
```

混合后，角色不会突然从站立姿势跳到跑步姿势。

骨骼矩阵最终会被用于 GPU 蒙皮：

```text
骨骼矩阵 + 顶点骨骼索引 + 顶点权重
    ↓
顶点着色器
    ↓
变形后的角色网格
```

### 阶段 6：场景系统更新 Transform

角色的位置、朝向、缩放通常保存在 `Transform` 组件中：

```cpp
Transform& transform = player.getComponent<Transform>();
transform.position = result.actualPosition;
transform.rotation = faceMoveDirection(moveDirection);
```

如果角色有子对象，例如武器和跟随相机：

```text
Player
├── RightHand
│   └── Sword
└── CameraAnchor
    └── PlayerCamera
```

场景图需要更新父子变换：

```text
玩家移动
    ↓
手、武器、相机锚点跟随
    ↓
相机与武器得到新的世界矩阵
```

这一步通常称为 **Transform Propagation（变换传播）**。

### 五、渲染一帧的完整过程

经过输入、逻辑、物理和动画更新后，场景数据已经是最新状态。接下来进入渲染阶段。

### 阶段 1：可见性判断

场景中可能有数千个物体，但相机只能看到其中一部分。

渲染系统会先判断：

```text
物体是否在相机视锥体内？
物体是否被完全遮挡？
物体距离是否过远？
是否应使用低精度模型？
```

最基础的技术是 **Frustum Culling（视锥裁剪）**。

相机可见区域可以近似理解为一个截头金字塔：

```text
近裁剪面
    ↓
可见区域逐渐变大
    ↓
远裁剪面
```

不在这个范围内的物体不需要提交给 GPU 绘制。

这样可以减少 Draw Call、三角形数量和 Shader 工作量。

### 阶段 2：组织渲染对象

渲染系统从场景中查询需要绘制的实体：

```text
有 Transform
且有 MeshRenderer
且已通过可见性判断
```

每个渲染对象至少需要：

```text
模型矩阵 Model Matrix
网格 Mesh
材质 Material
贴图 Texture
骨骼矩阵（如果是动画角色）
```

概念数据结构：

```cpp
struct RenderItem {
    Matrix4 modelMatrix;
    MeshHandle mesh;
    MaterialHandle material;
    SkeletonPoseHandle pose;
};
```

渲染器会按材质、网格或渲染队列分类，以减少 GPU 状态切换。

例如：

```text
不透明物体
    ↓
天空盒
    ↓
透明物体
    ↓
UI
    ↓
后处理
```

透明物体通常需要按距离排序，因为它们要和背景颜色混合。

### 阶段 3：阴影 Pass

若场景中存在会投射阴影的光源，通常先进行阴影渲染。

例如太阳光：

```text
从太阳的方向观察场景
    ↓
将可投影物体的深度写入 Shadow Map
    ↓
正常渲染时读取 Shadow Map
    ↓
判断像素是否被遮挡
```

因此“渲染一帧”不一定是只画一次场景，而可能有多个 **Render Pass（渲染通道）**。

一个典型顺序：

```text
Shadow Pass
    ↓
Depth Pre-pass（可选）
    ↓
Opaque Pass
    ↓
Skybox Pass
    ↓
Transparent Pass
    ↓
Post-processing Pass
    ↓
UI Pass
```

### 阶段 4：不透明物体渲染

渲染器将相机、光源和物体数据传给 GPU。

例如对角色模型：

```text
Model Matrix：角色在世界中的位置和姿态
View Matrix：相机视角
Projection Matrix：透视投影
Material：基础颜色、粗糙度、金属度
Textures：Albedo、Normal、AO 等贴图
Lights：方向光、点光等
Shadow Map：阴影深度图
Bone Matrices：角色骨骼矩阵
```

GPU 处理过程：

```text
顶点着色器
    ↓
先使用骨骼矩阵蒙皮角色顶点
    ↓
再使用 MVP 将顶点投影到屏幕
    ↓
光栅化生成片元
    ↓
片元着色器读取材质和贴图
    ↓
PBR 计算光照、反射和阴影
    ↓
输出 HDR 颜色
```

### 阶段 5：后处理与屏幕显示

主场景通常会先渲染到一张离屏纹理，而不是直接显示到屏幕。

这样可以继续执行后处理：

```text
HDR 场景颜色
    ↓
Bloom：提取和模糊亮区
    ↓
Tone Mapping：将 HDR 映射到显示器范围
    ↓
Anti-Aliasing：减轻锯齿
    ↓
Color Grading：调整整体色彩风格
    ↓
UI 叠加
    ↓
输出到屏幕 Back Buffer
```

最后调用显示接口，例如：

```cpp
window.present();
```

把当前帧提交给显示器。

### 六、资源系统在这一帧中做什么

资源系统不会只在“加载关卡时”工作。

例如玩家正在接近一个新区域：

```text
玩家靠近森林入口
    ↓
流式加载系统发现前方区域即将可见
    ↓
异步请求树木、岩石、环境音、贴图资源
    ↓
后台线程读取和解析数据
    ↓
创建可供渲染使用的资源
    ↓
玩家进入区域前，资源已准备好
```

同时，对于远离玩家的区域：

```text
区域不再可见
    ↓
对象从活动场景中移除或冻结
    ↓
不再使用的资源成为卸载候选
    ↓
释放内存和显存
```

这类机制叫作 **Streaming（流式加载）**。

开放世界游戏如果一次性加载整个地图，通常会占用过多内存、加载时间过长。因此它们常按区域动态加载和卸载内容。

```text
场景如何保存和加载？
```

#### 4. 找资源加载入口

搜索：

```text
Asset
Resource
Load
Import
Mesh
Texture
Shader
```

重点了解：

```text
资源是否通过路径、GUID 还是 Handle 引用？
是否有缓存？
加载是否同步？
纹理和模型如何变成 GPU 资源？
```

#### 5. 找渲染入口

搜索：

```text
Renderer
RenderSystem
RenderPass
Draw
Submit
CommandBuffer
```

重点了解：

```text
渲染器从哪里拿到场景对象？
如何筛选需要绘制的对象？
材质和 Shader 在哪里绑定？
最终 Draw Call 在哪里发出？
```

### 八、阅读代码时的正确目标

第一次阅读引擎代码时，不要追求“理解每一行”。

更有效的目标是：

```text
我知道模块在哪
我知道关键入口函数在哪
我知道数据从哪里进入
我知道数据由谁处理
我知道最终结果流向哪里
```

例如看到以下调用：

```cpp
renderer.render(scene, camera);
```

你暂时无法理解 `renderer` 内部所有细节也没有关系。先回答：

```text
scene 中有什么数据？
camera 提供什么数据？
render 后输出到哪里？
```

然后再逐步进入内部。

### 九、第五天的综合实践

下面的实践不需要从零写完整引擎。选择其中一个完成即可。

### 方案 A：用 Unity 或 Unreal 做一个最小 3D 场景

创建一个最小可交互场景：

```text
一个角色或立方体
一个地面
一个方向光
一个点光
一个 PBR 材质物体
一个碰撞墙
一个可控制相机
```

完成以下功能：

1. 按 `W/A/S/D` 移动角色或立方体。
2. 角色不能穿过墙。
3. 角色受到重力影响或可检测地面。
4. 物体能投射阴影。
5. 调整材质的 `Metallic` 和 `Roughness`，观察变化。
6. 开启或观察 HDR、Bloom、抗锯齿等后处理。
7. 用引擎性能分析器查看帧率、Draw Call 或 GPU 耗时。

这个实践能把前四天的大部分概念变成可观察的结果。

### 方案 B：阅读 GAMES104 或开源引擎的最小运行链路

选择一个能编译运行的样例，按下面路径做笔记：

```text
程序入口
    ↓
引擎初始化
    ↓
主循环
    ↓
场景加载
    ↓
实体和组件创建
    ↓
资源加载
    ↓
物理 / 动画更新
    ↓
渲染提交
    ↓
GPU 绘制
```

笔记不需要抄代码，只需为每个步骤记录：

```text
关键文件
关键类或函数
输入数据
输出数据
目前不理解的问题
```

示例表格：

| 环节 | 文件/类 | 输入 | 输出 |
|---|---|---|---|
| 程序入口 | `main.cpp` | 命令行参数、配置 | Engine 实例 |

### 方案 C：写一个最小“引擎流程模拟”程序

不使用 GPU，只用伪代码或普通程序模拟引擎模块调用顺序：

```cpp
while (running) {
    input.update();

    playerController.update(input);

    physics.move(player);
    animator.update(player.velocity);

    scene.updateTransforms();

    renderer.submit(player);
    renderer.submit(environment);
    renderer.render(camera);
}
```

为每个模块打印日志：

```text
[Input] W pressed
[Logic] Desired direction: Forward
[Physics] Actual velocity: 4.0
[Animation] State: Run
[Scene] Player position updated
[Renderer] Submitted Player mesh
[Renderer] Frame presented
```

这个练习的价值在于确认你理解了系统调用顺序和模块职责。

### 十一、5 天学习成果检查

完成第五天后，应该能够不看资料回答以下问题。

#### 1. 引擎运行

1. 游戏主循环为什么要不断执行？
2. `deltaTime` 的作用是什么？
3. 输入、逻辑、物理、动画和渲染大致以什么顺序执行？
4. 为什么物理系统通常要固定时间步更新？

#### 2. 场景与资源

1. 场景图和 ECS 分别解决什么问题？
2. Prefab 和场景中的实体有什么区别？
3. 为什么资源需要缓存、句柄和异步加载？
4. 为什么要把模型、贴图、动画从制作格式转换为运行时资源？

#### 3. 动画与物理

1. 骨骼、蒙皮、关键帧和动画状态机分别做什么？
2. 为什么动画和物理不能混为一个系统？
3. 什么是碰撞检测和碰撞响应？
4. 为什么角色常使用 Character Controller，而不是纯动态刚体？

#### 4. 渲染

1. 顶点如何从模型空间到达屏幕空间？
2. PBR 的 Metallic、Roughness 和 Normal Map 分别影响什么？
3. Shadow Map 的基本原理是什么？
4. HDR、Tone Mapping、Bloom 和抗锯齿分别解决什么问题？
5. Draw Call 多、模型面数高、Shader 复杂时，为什么可能降低性能？

### 十二、后续 2-4 周的实践路线

5 天完成的是游戏引擎知识框架。后续应选择一个方向深入，避免同时学习所有模块。

| 方向 | 建议实践 |
|---|---|
| 渲染 | 使用 OpenGL、Vulkan、DirectX 或 WebGPU，从三角形开始实现 Mesh、相机、PBR、阴影和后处理 |
| 引擎架构 | 实现最小 ECS、场景图、资源句柄、Prefab 序列化和事件系统 |
| 动画 | 实现骨骼层级、关键帧插值、动画状态机、Blend Tree 和 IK |
| 物理 | 学习碰撞体、空间划分、刚体、约束和 Character Controller |
| Unity/Unreal 工程 | 制作一个小型 3D 可玩场景，使用引擎已有系统并阅读其运行机制 |
| 工具链 | 制作场景编辑器、资源浏览器、属性面板、日志面板和性能统计工具 |

对零基础程序员，更推荐以下顺序：

```text
Unity / Unreal 基础实践
    ↓
复现一个最小渲染器或 ECS
    ↓
深入图形、动画或物理中的一个方向
    ↓
阅读更复杂的开源游戏引擎代码
```

### 第五天结束验收

用 5-10 分钟，不看笔记讲清楚下面这段流程：

> 游戏启动时，引擎初始化窗口、渲染、输入、资源、物理等系统，并加载初始场景。游戏运行时，每帧先读取玩家输入，再由游戏逻辑计算角色意图。角色控制器和物理系统根据碰撞、重力和地面状态计算真实位置与速度，动画状态机据此生成骨骼姿态。场景系统更新所有对象的世界变换，渲染系统筛选相机可见对象，准备模型、材质、光源、阴影和相机数据并提交给 GPU。GPU 对模型进行顶点变换、蒙皮、光栅化和 PBR 光照计算，最后再经过 HDR、Tone Mapping、Bloom 和抗锯齿等后处理，将最终画面显示到屏幕。
